# ADR 作成・更新

判断の重さに合わせて 2 種類の雛形を使い分け、ADR を作成・更新する。

| 雛形 | 本文の分量 | 使う場面 |
| --- | --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/skills/adr/_template-short.md`（簡易版） | 本文 10 行未満の文章 | 選択肢が 2〜3 個で、却下理由がそれぞれ 1 行で言える。影響範囲が限られる。やらない判断の多く |
| `${CLAUDE_PLUGIN_ROOT}/skills/adr/_template.md`（詳細版） | 100 行未満 | 選定基準が複数あり要因ごとに比較が要る。影響が広く、戻すのが大変。読み手に技術的な説明が要る |

迷ったら簡易版で書き始める。書いていて「理由が 1〜2 文に収まらない」「却下理由に説明が要る」「選定基準が 3 つ以上ある」となったら詳細版に切り替える。読みやすさを優先し、詳細版のセクションを埋めるために内容を水増ししない。

## 簡易版の書き方

- 本文（見出しより下）は **10 行未満**の文章で書く。見出し・箇条書き・表は使わない
- 段落は「背景 → 決定と理由 → 却下した案とトレードオフ」の順に 2〜3 段落にする。判断の種類はフロントマターの `type` に書く
- 短くても納得できる文章にする。決め手の根拠になる公式ドキュメント・一次情報があれば本文中にリンクし、決め手になった箇所を引用する（引用は `>` の 1〜2 行。英語の引用には和訳を添える）
- リンク・引用は判断を支えるものだけに絞る。飾りのために足さない
- 置き換える ADR・経緯の記録（障害報告・作業ログ・Issue）がある場合も、本文中にリンクとして入れる

記入例：

```markdown
# ADR 2026-06-03: service-split: 今はサービスを分割しない

チームは 3 人で、デプロイ対象も 1 つしかない。負荷の偏りが出ている機能も無いため、マイクロサービスへの分割を提案されたが、今それを行う必要があるかを判断した。

分割はしないと決めた。Martin Fowler は [MonolithFirst](https://martinfowler.com/bliki/MonolithFirst.html) で次のように述べており、境界が固まっていない今の段階に当てはまる。

> you shouldn't start a new project with microservices, even if you're sure your application will be big enough to make it worthwhile.（アプリが十分大きくなると確信していても、新しいプロジェクトをマイクロサービスで始めるべきではない）

モジュール境界だけはディレクトリで分けておき、特定の機能に負荷が偏った時点で、その機能から切り出す案を再検討する。
```

Markdown の書式は `${CLAUDE_PLUGIN_ROOT}/references/markdown.md` を Read し、その規約に従う。

## ADR にする判断

ADR は、時期（立ち上げ時かどうか）ではなく**判断の重さ**で起こす。次のどれかに当たる判断が対象。

- **戻すのが大変**：後から変えるとコストが大きい
- **影響が広い**：複数の人・複数の箇所がその判断に従う
- **理由が残らないと困る**：半年後に「なぜこうなっているのか」と聞かれ、答えられる人がいなくなる

| 判断の種類 | 例 |
| --- | --- |
| 新規の選定・方針 | 技術選定、モジュールの分け方・データの持ち方などの設計方針、テスト・ブランチ・デプロイなどの運用ルール |
| 既存の判断の変更 | リリース後に見つかった仕様上の問題で方式を変えた、要件・制約・コストの変化で方針を切り替えた |
| やらない判断 | 提案された構成・ツールを今は導入しないと決めた（再提案のたびに議論を繰り返さないため） |

ADR にしないもの：

- その場限りの実装上の選択（1 か所で閉じていて、変えてもすぐ戻せるもの）
- 障害や問題の経緯そのもの（何が起きて・どう復旧したか）。作業ログ・障害報告に書き、ADR の「経緯の記録」からリンクする。ADR に書くのは、その結果として**変えると決めた判断**だけ

ユーザーから題材が渡されたら、上の基準に当たるかを確認してから提案する。当たらない場合は、その旨と、代わりに書く場所（作業ログ・コードコメント等）を伝える。

## 作成前の承認（必須）

新規 ADR は**勝手に作成しない**。次の手順を必ず踏む。

1. 「どの決定を ADR 化するか」をユーザーに提案する（題材・採用案・却下案の要点と、簡易版・詳細版のどちらで書くかを示す）
2. ユーザーが**承認した時に初めて** `YYYY-MM-DD-*.md` を新規作成する
3. 承認なしにファイルを作成・コミットしない（他作業のついでに自動起票しない）

既存 ADR のステータス更新（承認済み・廃止・置き換え）も、判断が伴うため同様に提案→承認を経る。

## 出力先の決定

ADR ディレクトリはプロジェクトごとに異なる。次の順で解決する。

1. `docs/adr/` が存在すればそこを使う
2. 無ければ `doc/adr/`・`docs/decisions/`・`adr/` を Glob で探す
3. どれも無ければユーザーに出力先を確認する（**勝手にディレクトリを作らない**）

以降この Skill では、解決したディレクトリを `<ADR_DIR>` と表記する。

## 引数

末尾の `$ARGUMENTS` には以下を自由記述で渡す。空でも可（その場合は対話で不足を補う）。

| 項目 | 内容 |
| --- | --- |
| 題材 | 何の決定を ADR 化するか |
| 参考資料 | 既存メモ・関連ドキュメントの相対パス |
| 補足プロンプト | 強調したい論点・除外する範囲・引用してほしい一次情報など |

記入例:

```text
テスト戦略の採用判断。資料: tmp1.md, tmp2.md。テストトロフィー採用。ピラミッド・アイスクリームコーンの却下理由を明記すること。
```

## ファイル命名

- 形式: `YYYY-MM-DD-{kebab-case-subject}.md`
- 日付: ADR を作成した日。`date +%Y-%m-%d` で取得する。日付順に並ぶので、ファイル一覧がそのまま判断の履歴になる
- **判断の対象**（「何について決めたか」）で命名する。採用したツール名や結論は入れない。結論は変わりうるが、対象は変わらないため（置き換えの ADR も同じ対象名で、日付だけが違う形で並ぶ）

| 判断の種類 | 例（判断の対象） | ❌ NG（ツール名・結論） |
| --- | --- | --- |
| 新規の選定 | `2026-04-01-package-manager.md` / `2026-04-01-frontend-framework.md` | `2026-04-01-pnpm.md` / `2026-04-01-nextjs.md` |
| 設計・運用の方針 | `2026-05-12-authorization-layer.md` / `2026-05-20-branch-strategy.md` | `2026-05-12-check-auth-in-middleware.md` |
| 既存の判断の変更 | `2026-09-30-session-storage.md`（旧 ADR と同じ対象名にする） | `2026-09-30-switch-to-redis.md` |
| やらない判断 | `2026-06-03-service-split.md` | `2026-06-03-no-microservices.md` |

- 同じ日付・同じ対象名のファイルが既にある場合は作らず、既存 ADR の更新か、対象名を分けるかをユーザーに確認する
- `<ADR_DIR>` の既存 ADR が連番（`0001-*.md` 等）で命名されている場合は、混在させずにどちらへ揃えるかをユーザーに確認する。既存ファイルの改名はリンク切れを生むため、承認なしに行わない

## ステータス値

| 値 | 用途 |
| --- | --- |
| `提案中` | 作成直後・レビュー中（作成時のデフォルト） |
| `承認済み` | レビュー完了・Merge 可能になった時点 |
| `廃止` | 決定が不要になったとき |
| `[YYYY-MM-DD-subject](YYYY-MM-DD-subject.md) により置き換え済み` | 別 ADR で再決定したとき。新 ADR への相対パスリンクを必ず含める |

## 手順（新規作成）

1. 「出力先の決定」に従って `<ADR_DIR>` を確定する
2. `date +%Y-%m-%d` で日付を取得し、`ls <ADR_DIR>` で同じ日付・同じ対象名のファイルが無いこと、既存 ADR の命名規則を確認する
3. 承認された雛形（簡易版 `_template-short.md` / 詳細版 `_template.md`）の内容をコピーして `<ADR_DIR>/YYYY-MM-DD-{subject}.md` を作成する。見出しとフロントマターの `date` にも同じ日付を入れる。「判断の種類」（簡易版はフロントマターの `type`）は該当するものだけを残し、背景はその種類の書き方に従う。簡易版の角括弧のプレースホルダーは、情報が揃った段落だけを文章に置き換える
4. フロントマター `status: "提案中"` で開始する。**LLM が `承認済み` に変更することは絶対禁止**。承認はユーザーが判断する
5. 作成完了後、`<ADR_DIR>/README.md` に ADR 一覧テーブルがあれば**行を追加する**（無い場合はこの手順を飛ばす）
6. チャット履歴・引数から読み取れない情報は埋めない。「意思決定の要因」「検討した選択肢」「却下理由」「根拠」等が不足する場合は、**テンプレートのプレースホルダーまたはコメントをそのまま残す**。LLMが推測で補完しない

## 手順（既存の判断を変更する）

リリース後の問題や状況の変化で、既存 ADR の判断を変えるときの手順。旧 ADR の本文は書き換えず、新しい ADR を足して履歴として残す。

1. 置き換え対象の旧 ADR を Read し、何を決めていたかを確認する
1. 「手順（新規作成）」に従って新 ADR を作る
    - ファイル名は旧 ADR と同じ判断の対象名にする（例：旧 `2026-04-10-session-storage.md` → 新 `2026-09-30-session-storage.md`）
    - 判断の種類は「既存の判断の変更」にし、背景に元の判断と変える必要が出た経緯を書く
    - 「関連情報」の「置き換える ADR」に旧 ADR への相対リンクを書く。きっかけになった障害報告・作業ログ・Issue があれば「経緯の記録」にリンクする
1. 旧 ADR の `status` を `[YYYY-MM-DD-subject](YYYY-MM-DD-subject.md) により置き換え済み` に変更する（新 ADR への相対パスリンクを必ず含める）。本文への追記は一切しない
1. `<ADR_DIR>/README.md` の一覧テーブルがあれば、新 ADR の行を足し、旧 ADR のステータス列も同期する

新規作成と同じく、旧 ADR の status 変更を含めて提案 → 承認を経てから行う。

## 更新時のチェック

- **ADR の不変性**: 初回作成後の ADR は **フロントマター以外を変更しない**
- ステータス変更: フロントマター `status` を更新し、`<ADR_DIR>/README.md` のステータス列も同期する
- 決定を覆す場合: 「手順（既存の判断を変更する）」に従う

## レビューチェックリスト

作成・更新後に以下を確認する。

- [ ] ファイル名が判断の対象名になっている（ツール名・結論を使わない。例: `frontend-framework.md` ✅ / `nextjs.md` ❌、`service-split.md` ✅ / `no-microservices.md` ❌）
- [ ] 「判断の種類」が 1 つに絞られ、背景がその種類の書き方になっている
- [ ] 既存の判断の変更なら、「置き換える ADR」が旧 ADR にリンクし、旧 ADR の `status` が新 ADR にリンクしている
- [ ] フロントマター `status` がある（作成時は `提案中`だが最終的に`承認済み`または`廃止`にしなければならない）
- [ ] 関連 ADR のリンク切れがない（未作成なら「（予定）」付き）
- [ ] `<ADR_DIR>/README.md` の一覧テーブルを更新した（テーブルがある場合）
- [ ] 決定・理由・却下理由がエンジニア歴 1 年目でも読める平易さで書かれている
- [ ] バージョン指定がある場合、その理由が書かれている
- [ ] 簡易版なら本文が見出し・箇条書きなしの文章で 10 行未満に収まり、決め手に根拠のリンク・引用が付いている（収まらないなら詳細版に切り替える）。詳細版なら 100 行未満に収まっている

詳細版のみ：

- [ ] 意思決定の要因に前提条件が混入していない
- [ ] 決定の根拠が意思決定の要因ごとに書かれている
- [ ] 参考資料が「なし」または一次情報 URL で埋まっている（空欄 NG）
- [ ] 「検討した選択肢」のうち公式ページがある候補（ツール・ライブラリ・サービス）に公式リンクが付与されている
- [ ] 使用する参考資料は評価の高い日本語記事を優先。英文の公式ドキュメントの方が信頼性が高ければそちらを優先している
- [ ] 参考資料の各リンクに `— {タグ}: {1 行根拠}` 形式で信頼性根拠が付与されている

## 参考資料のタグ

参考資料の各リンクに `— {タグ}: {1 行根拠}` を付与する。

| タグ | 用途 |
| --- | --- |
| 一次情報 | 提唱者・開発元本人による記述 |
| 公式 | 公式ドキュメント・仕様書 |
| 解説 | 原典が直接参照しづらい場合の業界標準的な二次資料 |

記入例:

```markdown
- [The Testing Trophy](https://kentcdodds.com/...) — 一次情報: 戦略の提唱者 Kent C. Dodds 本人による定義
- [Test Pyramid - Martin Fowler](https://martinfowler.com/...) — 解説: 原典 Mike Cohn 著書の業界標準的な代替参照
```

## 禁止事項

- ❌ ユーザーの承認なしに ADR を新規作成する（必ず提案 → 承認を経る。「作成前の承認（必須）」参照）
- ❌ ADR ディレクトリが見つからないときに勝手に作成する（ユーザーに確認する）
- ❌ 新規作成時にステータスを「提案中」以外にする（「承認済み」への変更はユーザーが行う。LLMによる変更は絶対禁止）
- ❌ チャット履歴・引数から判断できない情報（意思決定の要因・検討した選択肢・却下理由・根拠など）をLLMが独自に補完する。ADRは人間が思考して作る成果物であり、形だけ整えた内容を生成してはならない。情報が不足するセクションはテンプレートのまま残す
- ❌ 新規 ADR を完成形として仕上げる。新規作成はひな形の状態にとどめ、最終的な確認・更新は人が行う
- ❌ 背景と問題提起に結論（「○○を採用する」）を書く
- ❌ 意思決定の要因に「○○採用済み」のような前提条件を混ぜる
- ❌ 抽象表現（具体的な事象・出典を添える）
- ❌ 参考資料を空のまま放置する（不要なら「なし」と明示する）
- ❌ 関連 ADR をリンク切れのまま放置する（「（予定）」を付ける）
- ❌ バージョン指定を理由なく書く（理由がなければ指定を外す）
- ❌ ファイル名に採用ツール名や結論を使う（判断の対象名を使う）
- ❌ 初回作成後の ADR の本文（フロントマター以外）を変更する。修正・追記・バナー追加・注記・置き換え通知・「再検討中」等の状態変化メモを本文に書かない。状態変化は新 ADR の起票と旧 ADR の `status` 更新（および README の一覧テーブル同期）で表現する
- ❌ `status` の置き換え表記でリンクを省略する（必ず新 ADR への相対パスリンク `[YYYY-MM-DD-subject](YYYY-MM-DD-subject.md)` を含める）
- ❌ 障害や問題の経緯そのもの（何が起きて・どう復旧したか）を ADR の本文として書く（作業ログ・障害報告に書き、「経緯の記録」からリンクする）

## 保守

`allowed-tools` に `Write`・`Edit` を含めていない。ADR ディレクトリはプロジェクトごとに異なりパスパターンを固定できないうえ、本 Skill は「ユーザー承認なしに作成しない」方針のため、白紙委任せず通常の許可プロンプトを通す。
