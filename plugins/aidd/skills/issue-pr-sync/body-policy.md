# 本文の更新方針（issue-pr-sync）

手順 3 で、Issue・PR の本文の更新後の全文を作るときに読む。PR 本文の「AI を使った確認」の欄は、`references/ai-check-lines.md` に従う。

## 共通

- 既存の本文がある場合は、書き換えではなく**追従**である。既存の構成と主張を壊さない。ただし、本文が 500 文字を超えていれば、構成と主張を残したまま全体を縮める（承認を取る）
- **既存の見出し構成を保つ。** テンプレート由来のセクションを削らない。空でも残す
- **背景・目的（Why）は原則そのまま残す。** 差分と明らかに矛盾する場合だけ、書き換えずにユーザーへ指摘する。500 文字に縮めるときも、言い換えて残す
- 既存本文に無い情報を推測で足さない。差分・コミット・レビューで裏が取れたものだけ書く
- **長さは `short-body.md` に従う。** 1 文・1 項目は 50 文字以内、本文全体は 500 文字以内にする（チェックリストと関連 Issue の節は数えない）。読み手が知らなくてよい経緯や実装の細部は書かない
- 本文が 500 文字を超えていれば、全体を縮める。見出し・背景・判断の理由は短くして残し、経緯・細部・重複を削る
- 似た項目が増えたら、羅列せずに 1 行へまとめる
- 書式は `markdown.md` に従う

## Issue 本文

- タスクリストがあれば、差分で**実装を確認できた項目だけ**チェックを入れる。確認できないものは外したままにする
- 着手後に増えた対応は、既存のタスクリストに項目として追記する。既存項目の文言は、500 文字に縮めるとき以外は変えない
- 対応しないと決まった項目は消さずに残す（判断の経緯が読めなくなるため）。縮めるときも、短くして残す

## PR 本文：追従のとき（本文がある）

- 「変更点」に、手順 2 のコミットと差分から**増えた分だけ**を追記する。既存の記述は、事実と食い違うときと、500 文字に縮めるとき以外は書き換えない
- レビュー対応は「変更点」に、何を直したかとして 1 行で書く。レビューコメントの引用や返信は書かない（PR 上に既にある）
- `Closes #<番号>` / `Ref:` の記述は勝手に付け替えない。関連 Issue が増えた場合のみ、追加の可否をユーザーに確認する
- チェックリストは、差分から確認できた項目のみチェックする（「AI を使った確認」の欄は、`ai-check-lines.md` に従う）

## PR 本文：新規作成のとき（本文が空）

- セクション構成は PR テンプレートに従う。テンプレートは `.github/PULL_REQUEST_TEMPLATE.md` → `.github/pull_request_template.md` → `.github/PULL_REQUEST_TEMPLATE/*.md` → `docs/PULL_REQUEST_TEMPLATE.md` の順に探す。どれも無ければ「概要 / 変更点 / 確認したこと」で構成する
- **概要**：Issue の目的と、この PR で実現したことを 1〜2 文で書く
- **変更点**：手順 2 のコミットと差分から、何を変えたかを箇条書きで書く。ファイル名・関数名の羅列にせず、「〇〇したとき、〇〇される」のように処理の流れで書く
- **チェックリスト・確認したこと**：差分や実行結果で確認できた項目だけチェックする。未確認の項目はチェックを外したまま残す（「AI を使った確認」の欄は、`ai-check-lines.md` に従う）
- 末尾に `Closes #<Issue番号>` を付ける。Issue のタスクに差分で確認できないものが残っていれば、付けるかを手順 4 で確認する（マージ時に Issue が自動で閉じるため）
- レビュワー向けの検証手順は書かない（`/aidd:pr-create` の検証コメントの役割）
