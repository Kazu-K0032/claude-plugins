# タイトルとサイドバーの更新方針（issue-pr-sync）

手順 3 で、タイトル・サイドバーの変更案を作るとき、手順 5 でサイドバーを反映するときに読む。

## タイトルの決まりを探す

タイトルの案を作る前に、リポジトリの決まりを探す。下の `[分類] 本文` は、決まりが無いリポジトリでの既定のため。決まりがあるのに既定を当てると、`[Bug] fix: 〜` のように 2 つの形が混ざる。

- `CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`（`.github/` も）・`docs/` を「タイトル」「title」で Grep し、Issue・PR のタイトルの書き方を決めた記述を読む
- `.github/ISSUE_TEMPLATE/*.yml` の `title:` を読む。接頭辞（`[Bug]: `・`Bug: ` など）があれば、そのフォームに当たる種類の Issue と PR では、その接頭辞に合わせる
- 決まりがあれば、その形でタイトルの案を作り、下の「タイトル」の書式と分類は当てない。ラベルは、下の表を使ってよい
- 決まりが無ければ、下の「慣習を探す」に進む
- どれに従ったか（決まりのファイルのパス、慣習、または「既定」）を、承認の画面と結果に書く。利用者が、取り違えていないかを確かめられるようにするため

### 慣習を探す

文書に決まりが無くても、題名の形が慣習でそろっているリポジトリがある（例：`【決済 | 請求書】〜`・`feat: 〜`）。慣習を見ずに既定を当てると、Issue ごとに分類を足す案が出て、利用者が毎回断ることになる。

1. 直近の題名を取る。手順 1 で取った Issue・PR は除く

    ```bash
    gh issue list --state all --limit 20 --json title
    gh pr list --state all --limit 20 --json title
    ```

1. 合わせて 10 件以上あり、その半分以上が同じ形の接頭辞（括弧で囲んだ語・`<語>:` など）で始まっていれば、慣習があるとみなす。下の「タイトル」の分類（`[Bug]` など）で始まる題名は、慣習に数えない。この方針で付けた題名を、慣習と取り違えないため
1. 慣習があれば、タイトルの変更案を作る前に `AskUserQuestion` で 3 つから選んでもらう。慣習は推測のため、決め打ちせず人に決めてもらう

    | 選択肢 | 中身 |
    | --- | --- |
    | 慣習に合わせる（推奨） | 見つけた形と、その形で作った案を示す。接頭辞の中身（領域の名前など）が題名や本文から分からなければ、案に入れず、自由記述で受ける |
    | 既定の分類を付ける | 下の「タイトル」に従う |
    | タイトルを変えない | タイトルの変更案を作らない。PR のタイトルは、今の Issue のタイトルにそろえる |

1. 慣習に合わせると選ばれたら、結果で、その形を `CONTRIBUTING.md` などに書くよう勧める。書けば、次から上の「決まり」として見つかり、聞かずに済むため。文書は直さず、勧めるだけにする
1. 慣習が無ければ、下の「タイトル」に従う

## タイトル

決まりが無いリポジトリでは、タイトルを `[分類] 本文` の形にする。Release の説明は PR のタイトルの一覧のため、分類があると、バグの修正か機能の追加かを開かずに見分けられる。

| 分類 | 使う場面 | ラベル |
| --- | --- | --- |
| `[Bug]` | 期待と違う動き・エラーを直す | `bug` |
| `[Feature]` | 機能を足す・変える、手順や仕組みを改善する | `feature`（無ければ `enhancement`） |
| `[Docs]` | 文書だけを足す・直す | `docs`（無ければ `documentation`） |
| `[Refactor]` | 外から見た振る舞いを変えずに、構造を直す | `refactor` |
| `[Release]` | リリースの Issue と、リリースの PR | `release` |
| `[Research]` | 調べて決める。実装を伴わない | `research` |
| `[Other]` | 上のどれにも当たらない（版を上げる、依存を更新するなど） | `other` |

- 本文は、何をするか・何が起きるかを動詞で終える 1 文にする（例：`[Bug] bot の保護パスの確認が、名前の変更を見落とす`）
- 版を上げる Issue・PR は `[Other]` にする。`release` ラベルの Issue はリリースのワークフローを動かし、`release` ラベルの PR はリリースノートから外れるため
- `[Retro]`（振り返りのフォーム）と、dependabot などツールが自動で作るタイトルは変えない
- Issue のタイトルが基準。閉じる Issue が 1 つなら、PR のタイトルは Issue のタイトルと**同じ文字列**にする
- 閉じる Issue が複数（PR 本文の「関連 Issue」に `Closes #<番号>` が 2 つ以上）なら、PR のタイトルを Issue にそろえない。Release の説明は PR のタイトルの一覧のため、1 つの Issue のタイトルではほかの変更が載らない
  - ほかの Issue は、`gh issue view <番号> --json title,body` で取る。手順 1 では引数の Issue しか取らないため
  - PR のタイトルが、どれか 1 つの Issue のタイトルと同じときだけ、全ての Issue の中身が伝わる案を作る（承認を取る）。分類は、Issue の分類がそろえばそれ、違えば主な変更の分類にし、どれに合わせたかを示す
  - それ以外は変えない。人が決めたタイトルを上書きしないため
- Issue のタイトルに分類が無ければ、頭に分類を足す案を作る（承認を取る）。言い回しは変えない。既存の書式（日付などの接頭辞）は、分類の後ろに残す
- Issue のタイトルの本文は、対応内容が変わって**今のタイトルでは中身が伝わらない**ときだけ直す。言い回しを整えるだけの変更はしない
- どちらも直す必要が無ければ「変更なし」

## サイドバー

`gh label list` で**リポジトリに実在するラベルだけ**を使う。存在しないラベル名を提案しない。

| 項目 | 変更案を出す条件 | 反映のしかた |
| --- | --- | --- |
| ラベル | タイトルの分類（リポジトリに決まりがあれば、中身から決めた種類）に合うラベル（上の表）が付いていないとき、または分類と食い違うラベルが付いているとき。Issue と PR で揃える。`release` は足さない（リリースのワークフローを動かすため） | `--add-label` / `--remove-label`。外すときは承認を取る |
| 担当者 | 未設定のとき。PR は Issue の担当者に、Issue も未設定なら `@me` に揃える。設定済みなら触らない | `--add-assignee` |
| レビュワー | 未設定で、かつリポジトリに CODEOWNERS があるとき。CODEOWNERS から差分の所有者を選ぶ | `gh pr edit --add-reviewer`。通知が届くため承認を取る |
| マイルストーン | Issue に設定があり、PR が未設定のとき（Issue に揃える）。Issue も未設定なら提案しない | `gh pr edit --milestone` |
| Projects | 提案しない（`gh` の権限スコープとプロジェクトの運用に依存するため） | — |

Development セクションの Issue 紐付けは、`gh` の `edit` サブコマンドでは設定できない。必要なら PR 本文の `Closes #<番号>` で代替できる旨を添え、手動での紐付けを案内するにとどめる。

## サイドバーの反映

反映する項目をまとめて反映する（例）。

```bash
gh issue edit <Issue> --add-label feature --add-assignee @me
gh pr edit <PR> --add-label feature --add-assignee @me --add-reviewer <ユーザー名> --milestone "<マイルストーン名>"
```
