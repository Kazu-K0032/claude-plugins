# Issue / PR の同期更新

既存の Issue と PR の**根幹（背景・目的・解決方針）は正しい**前提で、そこから増えた差分を追従させる。想定する場面は、着手後に追加対応が入った・レビュー指摘に対応した結果、記述が実態とずれたとき。PR 本文が空の場合は、Issue と差分から本文を新規に作る。

既存の本文がある場合は、書き換えではなく**追従**である。既存の構成と主張を壊さない。

| 対象 | 反映のしかた |
| --- | --- |
| Issue / PR の本文 | 更新案（PR 本文が空なら新規の本文）を提示し、承認を取ってから `gh` で直接反映する |
| Issue / PR のタイトル | 対応内容とずれていれば直す案を、PR が Issue と違えば揃える案を提示し、承認を取ってから反映する |
| サイドバー（ラベル・担当者・レビュワー・マイルストーン） | 変更案を提示し、承認を取ってから反映する |

`/aidd:pr-create` との使い分け：

| スキル | 作るもの | GitHub への反映 |
| --- | --- | --- |
| `/aidd:pr-create` | PR 本文の提案と、レビュワー向けの動作検証ファイル（検証コメント） | しない（`tmp/` に下書きを出すだけ） |
| `/aidd:issue-pr-sync` | Issue / PR の本文・タイトル・サイドバーの更新 | 承認後に直接反映する |

| ファイル | 役割 |

## バリデーション

- `$ARGUMENTS` から Issue と PR の識別子を 2 つ取れない場合は、どちらが不足しているかを示して追加質問する
- 識別子は番号でも URL でもよい。`gh` は両方を受け付けるため、パースせずそのまま渡す
- `gh issue view` / `gh pr view` が失敗したら、その時点で中断して原因を報告する（存在しない・権限が無い・リポジトリが違う）

## 手順

### Step 1: 現状を集める

```bash
git branch --show-current
date +%Y%m%d_%H%M%S
gh issue view <Issue> --json number,title,body,labels,assignees,milestone,state,url
gh pr view <PR> --json number,title,body,labels,assignees,milestone,reviewRequests,reviews,comments,baseRefName,state,isDraft,url
gh label list
```

インラインのレビュースレッドは `gh pr view --json reviews` に本文が含まれないことがある。未解決の指摘を取りこぼしそうなときだけ `gh api repos/{owner}/{repo}/pulls/<PR>/comments` で補う。

PR 本文が空（空白のみを含む）なら「新規作成」、それ以外は「追従」として以降を進める。

### Step 2: 差分を読む

```bash
git log --oneline <baseRefName>..HEAD
git diff <baseRefName>...HEAD --stat
git diff <baseRefName>...HEAD
```

`baseRefName` は Step 1 の PR 情報から取る。ローカルに base ブランチが無い場合は `gh pr diff <PR>` に切り替える。

### Step 3: 更新案を作る

次の 4 つを組み立てる。

1. Issue 本文の更新後の全文（「本文の更新方針」）
1. PR 本文の更新後の全文。空なら新規の本文（「PR 本文」の「新規作成のとき」）
1. Issue / PR タイトルの変更案（「タイトルの方針」）
1. サイドバーの変更案（「サイドバーの更新方針」）

本文は `tmp/<ブランチ名>/issue-pr-sync_<ts>_issue.md` / `_pr.md` に書き出す。ブランチ名の `/` は `-` に置換する（規約は `aidd` の `README.md` の「ブランチ名の `/` は `-` に置き換える」）。

更新が不要と判断した対象があれば、無理に変更を作らず「変更なし」とする。

### Step 4: 承認を取る

`AskUserQuestion` で、対象ごとに**反映してよいか**を確認する。提示するのは次の 4 つ（「変更なし」の対象は質問しない）。

1. Issue 本文の変更点（どのセクションに何を足した / 直したかを箇条書きで。全文は出さない）
1. PR 本文の変更点（同上。新規作成のときはセクション構成と要点）
1. Issue / PR タイトルの変更（それぞれ変更前 → 変更後）
1. サイドバーの変更（Issue・PR それぞれについて、追加・削除する項目を列挙）

既存の記述と差分が食い違っていて、どちらを正とするか決めきれない論点があれば、承認を求める前にユーザーへ提示して判断を仰ぐ。

### Step 5: 反映する

承認された対象だけを反映する。`--body` に長文を直接渡すとシェルの引用で壊れるため、本文は必ずファイル経由で渡す。

```bash
gh issue edit <Issue> --body-file tmp/<ブランチ名>/issue-pr-sync_<ts>_issue.md
gh pr edit <PR> --body-file tmp/<ブランチ名>/issue-pr-sync_<ts>_pr.md
gh issue edit <Issue> --title "<新しいタイトル>"
gh pr edit <PR> --title "<Issue のタイトル>"
```

サイドバーは承認された項目だけをまとめて反映する（例）。

```bash
gh issue edit <Issue> --add-label enhancement --add-assignee @me
gh pr edit <PR> --add-label enhancement --add-assignee @me --add-reviewer <ユーザー名> --milestone "<マイルストーン名>"
```

反映前の本文・タイトル・サイドバーは Step 1 で取得済みなので、戻す必要が出たときのために変更前の値と出力パスを報告に残す。

### Step 6: 報告する

- 反映した対象と、その URL
- 変更前の値（タイトル・サイドバー）と、反映前の本文を戻すための出力パス
- 反映しなかった対象と、その理由
- 判断を保留した論点があればその内容
- PR 本文を新規作成した場合は、最後に次の旨を添える

  > PR 本文の提案とレビュワー向けの動作検証ファイルを作りたい場合は `/aidd:pr-create` を使う（GitHub には反映せず `tmp/` に下書きを出す）。今回のように本文・タイトル・サイドバーを直接整えたい場合は `/aidd:issue-pr-sync`。目的に応じて使い分ける

## 本文の更新方針

### 共通

- **既存の見出し構成を保つ。** テンプレート由来のセクションを削らない。空でも残す
- **背景・目的（Why）は原則そのまま残す。** 差分と明らかに矛盾する場合だけ、書き換えずにユーザーへ指摘する
- 既存本文に無い情報を推測で足さない。差分・コミット・レビューで裏が取れたものだけ書く
- **簡潔さと読みやすさを優先する。** 1 項目 1 行・1 文 1 事柄で書き、読み手が知らなくてよい経緯や実装の細部は書かない
- 似た項目が増えたら、羅列せずに 1 行へまとめる
- 書式は `${CLAUDE_PLUGIN_ROOT}/references/markdown.md` に従う

### Issue 本文

- タスクリストがあれば、差分で**実装を確認できた項目だけ**チェックを入れる。確認できないものは外したままにする
- 着手後に増えた対応は、既存のタスクリストに項目として追記する。既存項目の文言は変えない
- 対応しないと決まった項目は消さず、そのまま残す（判断の経緯が読めなくなるため）

### PR 本文

#### 追従のとき（本文がある）

- 「変更点」に、Step 2 のコミットと差分から**増えた分だけ**を追記する。既存の記述は、事実と食い違っていない限り書き換えない
- レビュー対応は「変更点」に、何を直したかとして 1 行で書く。レビューコメントの引用や返信は書かない（PR 上に既にある）
- `Closes #<番号>` / `Ref:` の記述は勝手に付け替えない。関連 Issue が増えた場合のみ、追加の可否をユーザーに確認する
- チェックリストは、差分から確認できた項目のみチェックする

#### 新規作成のとき（本文が空）

- セクション構成は PR テンプレートに従う。テンプレートは `.github/PULL_REQUEST_TEMPLATE.md` → `.github/pull_request_template.md` → `.github/PULL_REQUEST_TEMPLATE/*.md` → `docs/PULL_REQUEST_TEMPLATE.md` の順に探す。どれも無ければ「概要 / 変更点 / 確認したこと」で構成する
- **概要**：Issue の目的と、この PR で実現したことを 1〜2 文で書く
- **変更点**：Step 2 のコミットと差分から、何を変えたかを箇条書きで書く。ファイル名・関数名の羅列にしない
- **チェックリスト・確認したこと**：差分や実行結果で確認できた項目だけチェックする。未確認の項目はチェックを外したまま残す
- 末尾に `Closes #<Issue番号>` を付けるかを Step 4 でユーザーに確認する（マージ時に Issue が自動で閉じるため）
- レビュワー向けの検証手順は書かない（`/aidd:pr-create` の検証コメントの役割）

## タイトルの方針

- Issue のタイトルが基準。PR のタイトルは Issue のタイトルと**同じ文字列**にする
- Issue のタイトルは、対応内容が変わって**今のタイトルでは中身が伝わらない**ときだけ直す。言い回しを整えるだけの変更はしない
- 直すときは、何をするかが一読で分かる短い名詞句にする。既存の書式（日付などの接頭辞）は残す
- どちらも直す必要が無ければ「変更なし」

## サイドバーの更新方針

`gh label list` で**リポジトリに実在するラベルだけ**を使う。存在しないラベル名を提案しない。

| 項目 | 変更案を出す条件 | 反映のしかた |
| --- | --- | --- |
| ラベル | 差分の性質（バグ修正・機能追加・ドキュメント等）と現在のラベルが食い違うとき。Issue と PR で揃える | `--add-label` / `--remove-label`。外すラベルは承認時に明示する |
| 担当者 | 未設定のとき。PR は Issue の担当者に、Issue も未設定なら `@me` に揃える。設定済みなら触らない | `--add-assignee` |
| レビュワー | 未設定で、かつリポジトリに CODEOWNERS があるとき。CODEOWNERS から差分の所有者を選ぶ | `gh pr edit --add-reviewer` |
| マイルストーン | Issue に設定があり、PR が未設定のとき（Issue に揃える）。Issue も未設定なら提案しない | `gh pr edit --milestone` |
| Projects | 提案しない（`gh` の権限スコープとプロジェクトの運用に依存するため） | — |

Development セクションの Issue 紐付けは `gh` の `edit` サブコマンドでは設定できない。必要なら PR 本文の `Closes #<番号>` で代替できる旨を添え、手動での紐付けを案内するに留める。

## 判断基準

- 根幹が間違っている（目的そのものが変わった）と判断したら、追従ではなく作り直しなので、その旨を報告して中断する
- 差分が空、またはレビュー指摘が無く既存本文・タイトル・サイドバーと実態が一致している場合は「更新不要」と報告して終わる。形だけの更新を作らない
- PR が `merged` / `closed` の場合は何も変更せず、理由を報告して終わる

## 禁止事項

- ❌ 承認を取る前に `gh issue edit` / `gh pr edit` を実行すること
- ❌ 承認されていないサイドバーの項目を変更すること（特に、既存のラベル・担当者を外すこと）
- ❌ Projects を変更すること
- ❌ 既存本文の見出し・セクションを削ること
- ❌ 差分から確認できない項目にチェックを入れること
- ❌ レビューコメントへ返信を投稿すること
- ❌ 既存の本文を全面的に書き直すこと（本文がある場合は追従であり、作り直しではない）
- ❌ 対応内容が変わっていないのに、タイトルを言い換えること
