# PR本文と検証コメントの作成

現在のブランチのコミット内容とIssueの情報を元に、次の 2 つを生成する。どちらも投稿せず `tmp/` に下書きとして出力する。

- **PR 本文**: リポジトリの PR テンプレートに合わせた下書き
- **検証コメント**: レビュワーが自分の手で検証できるようにする、PR 本文とは別のコメント

## 参照ファイル

| ファイル | 役割 |
| --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/skills/pr-create/verify-comment-template.md` | 検証コメントの出力フォーマットと書き方 |

## PR テンプレートの解決

1. `.github/PULL_REQUEST_TEMPLATE.md` があればそれを使う
2. 無ければ `.github/pull_request_template.md`・`.github/PULL_REQUEST_TEMPLATE/*.md`・`docs/PULL_REQUEST_TEMPLATE.md` を Glob で探す
3. どれも無ければ「概要 / 変更点 / 関連 Issue / チェックリスト」の 4 セクションで構成し、テンプレートが無かったことを報告に含める

## バリデーション

- `$ARGUMENTS` が空の場合は追加質問する
- `gh issue view` で番号の実在を確認する

## 手順

1. `git branch --show-current` で現在のブランチ名を取得する（出力パス用）
2. `date +%Y%m%d_%H%M%S` でタイムスタンプを取得する
3. `gh issue view $ARGUMENTS` でIssueの内容（タイトル・本文・タスク）を取得する
4. `git log --oneline main..HEAD` で現在のブランチのコミット一覧を取得する（既定ブランチが `main` でない場合はそのブランチ名に読み替える）
5. `git diff main...HEAD --stat` で変更ファイルの概要を取得する
6. 「PR テンプレートの解決」で確定したテンプレートのセクション構成に合わせてPR本文を作成する。本文は `## 概要` から始め、タイトルは本文に含めない
7. `git diff main...HEAD` で差分本体を読み、「[チェック項目の洗い出し](#チェック項目の洗い出し)」の表を上から全て当てて条件分岐を列挙する
8. `${CLAUDE_PLUGIN_ROOT}/skills/pr-create/verify-comment-template.md` に従って検証コメントを作成する。既存 PR があれば `gh pr view --json number` で番号を埋める
9. `tmp/<ブランチ名>/pr-create_<yyyymmdd_hhmmss>.md`（PR本文）と `tmp/<ブランチ名>/pr-verify_<yyyymmdd_hhmmss>.md`（検証コメント）を**常に両方**出力し、2 つの出力パスと**別途 PR タイトル案（Conventional Commits 形式）**をユーザーに報告する

## PR本文の作成方針

テンプレートのセクションを埋める。HTMLコメントの誘導文は最終本文に残さない。

- **概要**: Why（背景・課題）/ What（実現したこと）。Issue 本文とコミットの事実に基づく
- **変更点**: コミット一覧（手順 4）を元に箇条書き。ファイル名・関数名の羅列ではなく「何を変えたか」を書く
- **関連 Issue**: テンプレートに合わせ `Closes #<Issue番号>` 形式で記載する（マージ時に Issue を自動クローズする。自動クローズが不要な場合のみ `Ref: Issue #<番号>` への変更をユーザーに促す）
- **チェックリスト**: テンプレートの項目をそのまま残し、コミット内容から確認できた項目のみチェックを入れる。未確認はチェックを外したままにする（セクション名はテンプレート側の見出しに従う）

## 検証コメントの作成方針

レビュワーに求めるのは次の 3 点に限る。細かいコードの仕様は対象にしない（AI 駆動開発の前提で粒度を下げない）。

1. **検証**: マージ前にレビュワーが手を動かして確かめられるか（コマンド実行・管理画面の操作・ローカルの画面確認）
2. **照合**: PR 本文の主張のうち、マージ前に確かめられるものがチェック項目に落ちているか
3. **網羅**: 条件が分かれるものは「そうでない場合」も項目にし、1 つずつ潰せるか

- 出力形式は `verify-comment-template.md` に従う。テンプレートに無いセクションを足さない
- 次の情報は**書かない**。それぞれ別に唯一の情報源があるため、パス表記でポインタを示すに留める

  | 書かない情報 | 参照先の例 |
  | --- | --- |
  | CI が自動検査する項目（必須ジョブの内訳） | CI 構成のドキュメント・`.github/workflows/` |
  | 技術別のレビュー観点 | `.github/instructions/`・コーディング規約 |
  | 重大度分類・網羅的コードレビューの結果 | コードレビュー用の Skill / workflow |
  | Issue タスクと実装の照合結果 | Issue のタスクリスト |
  | デザイン目視チェック項目 | デザインシステムの規約 |
  | 公開後の確認観点 | 運用手順書 |

- 実装と受け入れ基準のどちらを正とするか決めきれない論点は、検証コメントに書かず手順 9 の報告でユーザーに伝える

## チェック項目の洗い出し

差分に次の signal があれば、対応するチェック項目を立てる。上から全て当てる。

| 差分の signal | 立てるチェック項目 |
| --- | --- |
| ロジック・条件分岐の追加 | 該当機能を操作し、真・偽の両方が期待どおりになるか |
| 早期 return ガード（`*_exists` / `defined` 等）・環境変数による分岐 | no-op 側・動作側のどちらになるか |
| データモデル・スキーマ・入力項目の追加/必須化/型変更 | 入力あり・未入力を試したとき、バリデーションと表示がどうなるか |
| ルーティング・URL 構造の変更 | 該当 URL を開いたとき表示されるか（キャッシュ/ルート再生成後） |
| テンプレート・スタイルの変更 | 該当画面が崩れないか（狭い画面も） |
| Lint / 静的解析 / テストの設定変更 | 該当コマンドを実行したときエラーが出ないか |
| CI ワークフローのステップ追加 | ステップと同じコマンドをローカルで実行したとき通るか |
| 初期データ・マイグレーションの変更 | 投入・適用を実行したときエラーが出ず、期待どおりのデータが入るか |
| 依存パッケージ・ビルド設定の変更 | ビルドが成功し、画面が崩れないか |

プロジェクト固有の signal（特定のプラグイン設定・管理画面の挙動など）は、そのリポジトリの規約から読み取って追加する。

差分に signal があっても、マージ前に確かめられないもの（デプロイの発火・サーバー上のファイル状態・スケジュール実行の結果）は項目にしない。それらは PR 本文の「変更点」で説明する。

スキーマ・初期データ・ビルド成果物・ルーティング・依存パッケージの変更が差分に含まれるときは、チェック項目を試す前に必要な準備を「前提条件」に書く（判断表は `verify-comment-template.md` の「前提条件の書き方」）。

## 判断基準

- 推測ではなく、コミット内容とIssueの事実に基づいて記載する
- 出力先は `tmp/` 配下。下書きであり、PR 投稿はユーザーが内容を確認してから行う
- リポジトリのコミット規約がある場合は、その Why/What と整合させる

## 禁止事項

- ❌ 検証コメントを PR 本文に混ぜること（別ファイル・別用途）
- ❌ PR 本文の説明文をそのまま再掲すること（チェック項目は「確かめる操作と結果」で書く）
- ❌ マージ後にしか確認できない項目を書くこと
- ❌ CI の必須ジョブが検証済みのことを項目にすること（PR で自動的に落ちるため確認が重複する）
- ❌ テンプレートに無いセクションを足すこと
- ❌ ガード節・条件分岐を触った差分で「そうでない場合」の項目が無いまま出力すること
- ❌ チェックボックスを埋めた状態で出力すること（埋めるのはレビュワー）
