# 検証コメントの書き方

`pr-create` Skill が `tmp/<ブランチ名>/pr-verify_<yyyymmdd_hhmmss>.md` に書き出す、レビュワー向け検証コメントの方針と出力形式を定義する。`pr-create` の手順 8 でチェック項目を洗い出すとき、手順 9 で検証コメントを書くときに読む。この文書の「手順 N」は、`pr-create` の `SKILL.md` の手順を指す。

## 目次

- 方針
- チェック項目の洗い出し
- テンプレート
- 前提条件の書き方
- チェック項目の書き方

## 方針

レビュワーに求めるのは次の 3 点に限る。細かいコードの仕様は対象にしない（AI 駆動開発の前提で粒度を下げない）。

1. **検証**：マージ前にレビュワーが手を動かして確かめられるか（コマンド実行・管理画面の操作・ローカルの画面確認）
1. **照合**：PR 本文の主張のうち、マージ前に確かめられるものがチェック項目に落ちているか
1. **網羅**：条件が分かれるものは「そうでない場合」も項目にし、1 つずつ潰せるか

次の情報は**書かない**。それぞれ別に唯一の情報源があるため、パス表記でポインタを示すにとどめる。

| 書かない情報 | 参照先の例 |
| --- | --- |
| CI が自動検査する項目（必須ジョブの内訳） | CI 構成のドキュメント・`.github/workflows/` |
| 技術別のレビュー観点 | `.github/instructions/`・コーディング規約 |
| 重大度分類・網羅的コードレビューの結果 | コードレビュー用の Skill / workflow |
| Issue タスクと実装の照合結果 | Issue のタスクリスト |
| デザイン目視チェック項目 | デザインシステムの規約 |
| 公開後の確認観点 | 運用手順書 |

実装と受け入れ基準のどちらを正とするか決めきれない論点は、検証コメントに書かず、手順 12 の報告でユーザーに伝える。

## チェック項目の洗い出し

差分に次の signal があれば、対応するチェック項目を立てる。上から全て当てる。

| 差分の signal | 立てるチェック項目 |
| --- | --- |
| ロジック・条件分岐の追加 | 該当機能を操作し、真・偽の両方が期待どおりになるか |
| 早期 return ガード（`*_exists` / `defined` 等）・環境変数による分岐 | no-op 側・動作側のどちらになるか |
| データモデル・スキーマ・入力項目の追加/必須化/型変更 | 入力あり・未入力を試したとき、バリデーションと表示がどうなるか |
| ルーティング・URL 構造の変更 | 該当 URL を開いたとき表示されるか（キャッシュ/ルート再生成後） |
| テンプレート・スタイルの変更 | 該当画面が崩れないか（狭い画面も） |
| Lint / 静的解析 / テストの設定変更 | 該当コマンドを実行したときエラーが出ないか |
| CI ワークフローのステップ追加 | ステップと同じコマンドをローカルで実行したとき通るか |
| 初期データ・マイグレーションの変更 | 投入・適用を実行したときエラーが出ず、期待どおりのデータが入るか |
| 依存パッケージ・ビルド設定の変更 | ビルドが成功し、画面が崩れないか |

- プロジェクト固有の signal（特定のプラグイン設定・管理画面の挙動など）は、そのリポジトリの規約から読み取って足す
- 差分に signal があっても、マージ前に確かめられないもの（デプロイの発火・サーバー上のファイル状態・スケジュール実行の結果）は項目にしない。それらは PR 本文の「変更点」で説明する
- スキーマ・初期データ・ビルド成果物・ルーティング・依存パッケージの変更が差分に含まれるときは、チェック項目を試す前に必要な準備を「前提条件」に書く（判断表は「前提条件の書き方」）

## テンプレート

以下のテンプレートに沿うこと。それ以外の項目を勝手に追加しないこと。

```md
## 前提条件

- xxxxされていること

## チェック項目

### 〇〇について

- [ ] xxxxしたとき、xxxxになるか
- [ ] xxxxしたとき、xxxxになるか

### 〇〇について

- [ ] xxxxしたとき、xxxxになるか
- [ ] xxxxしたとき、xxxxになるか
```

## 前提条件の書き方

チェック項目を試す前に必要な、**このブランチ特有の準備**だけを書く。

- ブランチの切り替え・`git pull`・開発環境の起動・管理画面へのログインといった大前提は書かない
- 差分の内容から必要な準備を判断する

  | 差分に含まれるもの | 前提条件に書くこと |
  | --- | --- |
  | スキーマ・フィールド定義の追加・変更 | 定義を取り込み済みであること（インポート・マイグレーション適用） |
  | 初期データ・シードデータ | データを再投入していること |
  | フロントのアセット（CSS / JS のソース） | ビルドを実行し、成果物が更新されていること |
  | ルーティング・URL 構造 | ルートのキャッシュ再生成を実行していること |
  | 依存パッケージの追加・更新 | パッケージのインストールを実行していること |
  | プラグイン・拡張の設定に依存する機能 | 対象を有効化し、設定を入れていること |

- 準備が要らないときは `- なし` と 1 行書く

## チェック項目の書き方

- **マージ前にレビュワーが自分で確かめられることだけを書く**。マージ後にしか分からないこと（デプロイの発火、サーバー上のファイル状態、スケジュール実行の結果）は項目にしない
- **CI の必須ジョブが検証する範囲は書かない**。PR で自動的に落ちるため、レビュワーがやる意味がない
  - 書かない: Lint / 静的解析 / 自動テストのスペックが見ている挙動 / テスト前に走る前処理 / 秘匿情報の混入
  - 書く: CI がカバーしないもの。本番相当の依存が要る管理画面の挙動・特定環境でしか動かない JS・ドキュメントのリンク切れ
- 項目は「〇〇したとき、〇〇になるか」の疑問形で書く。レビュワーが Yes / No を判定できる粒度にする
- 長さの上限は無い。項目の数は差分で決まるため。1 項目は、1 つの確かめる操作と結果だけにする
- 粒度は簡易でよい。次のような手を動かせば分かるレベルに寄せる
  - `〇〇コマンドを実行したとき、エラーが出ないか`
  - `管理画面で〇〇を作るとき、〇〇というバリデーションがかかるか`
  - `ローカルで〇〇のページを開いたとき、〇〇が表示されるか`
- 見出しは変更のまとまり（機能・ワークフロー・ファイル群）ごとに分ける
- チェックボックスは**空欄のまま出力する**（埋めるのはレビュワー）
