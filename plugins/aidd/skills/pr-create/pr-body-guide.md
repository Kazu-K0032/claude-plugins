# PR 本文の書き方（pr-create）

`pr-create` の手順 7 で、PR 本文を書くときに読む。この文書の「手順 N」は、`pr-create` の `SKILL.md` の手順を指す。

## テンプレートを探す

`references/pr-template.md` の順で探す。見つからなければ、同じファイルの 4 つの節で書き、テンプレートが無かったことを報告に含める。

## 全体

- テンプレートの節を埋める。HTML コメントの誘導文は、最終の本文に残さない
- リポジトリの規約が PR 本文に節を求めていれば（例：「テストケース」）、テンプレートに無くてもその節を足す。規約とテンプレートがずれていても、規約を守るため。探し方は `references/repo-rules.md` に従い、話題の語は「PR の説明」「PR description」「セクション」「テストケース」にする
  - 置く場所は、規約が決めていればそれに従い、無ければ「変更点」の後（「関連 Issue」の前）にする
  - 足した節と、根拠にした規約のファイルを、手順 12 の報告に書く
- 長さは、リポジトリに本文の決まりがあればそちら、無ければ `short-body.md` に従う（探し方は `short-body.md` の「リポジトリに決まりがあるとき」）。`short-body.md` に従うときは、概要（最初の節）を 300 文字以内にする。概要より後の節（変更点など）は上限なし。経緯・重複・推測・Files changed で見られる細部は書かない
- リポジトリにコミットの規約がある場合は、その Why/What と整合させる

## 節ごとの書き方

- **概要**：Why（背景・課題）/ What（実現したこと）。Issue の本文とコミットの事実に基づく
- **変更点**：コミットの一覧（手順 5）を元に箇条書きにする。ファイル名・関数名の羅列ではなく、「〇〇したとき、〇〇される」のように処理の流れで書く。細部は「Files changed」に任せる
- **関連 Issue**：テンプレートに合わせ、`Closes #<Issue番号>` の形で書く（マージ時に Issue を自動で閉じる）。Issue が複数あれば、番号ごとに 1 行ずつ書く。自動で閉じなくてよい場合だけ、`Ref: Issue #<番号>` への変更をユーザーに促す
  - マージ先が既定ブランチでないときは、GitHub はマージで Issue を閉じない。リポジトリの規約（`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`）と `.github/workflows/` を「Issue」「閉じる」「close」で Grep し、マージで Issue を閉じる仕組みが無ければ、マージの後に手で閉じるよう報告に書く。仕組みがあれば書かない
- **チェックリスト**：テンプレートの項目をそのまま残し、コミットの内容から確かめられた項目だけにチェックを入れる。確かめていない項目は、チェックを外したままにする（節の名前はテンプレートの見出しに従う）
- **AI を使った確認**：テンプレートにこの欄があれば、`ai-check-lines.md` に従って、各コマンドに番号を入れる
