# PR 本文の書き方（pr-create）

`pr-create` の手順 7 で、PR 本文を書くときに読む。この文書の「手順 N」は、`pr-create` の `SKILL.md` の手順を指す。

## テンプレートを探す

1. `.github/PULL_REQUEST_TEMPLATE.md` があれば、それを使う
1. 無ければ、`.github/pull_request_template.md`・`.github/PULL_REQUEST_TEMPLATE/*.md`・`docs/PULL_REQUEST_TEMPLATE.md` を Glob で探す
1. どれも無ければ、「概要 / 変更点 / 関連 Issue / チェックリスト」の 4 つの節で書き、テンプレートが無かったことを報告に含める

## 全体

- テンプレートの節を埋める。HTML コメントの誘導文は、最終の本文に残さない
- 長さは `short-body.md` に従う。1 文・1 項目は 50 文字以内、本文全体は 500 文字以内にする（チェックリストと関連 Issue の節は数えない）
- リポジトリにコミットの規約がある場合は、その Why/What と整合させる

## 節ごとの書き方

- **概要**：Why（背景・課題）/ What（実現したこと）。Issue の本文とコミットの事実に基づく
- **変更点**：コミットの一覧（手順 5）を元に箇条書きにする。ファイル名・関数名の羅列ではなく、「〇〇したとき、〇〇される」のように処理の流れで書く。細部は「Files changed」に任せる
- **関連 Issue**：テンプレートに合わせ、`Closes #<Issue番号>` の形で書く（マージ時に Issue を自動で閉じる）。自動で閉じなくてよい場合だけ、`Ref: Issue #<番号>` への変更をユーザーに促す
  - マージ先が既定ブランチでないときは、GitHub はマージで Issue を閉じない。リポジトリの規約（`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`）と `.github/workflows/` を「Issue」「閉じる」「close」で Grep し、マージで Issue を閉じる仕組みが無ければ、マージの後に手で閉じるよう報告に書く。仕組みがあれば書かない
- **チェックリスト**：テンプレートの項目をそのまま残し、コミットの内容から確かめられた項目だけにチェックを入れる。確かめていない項目は、チェックを外したままにする（節の名前はテンプレートの見出しに従う）
- **AI を使った確認**：テンプレートにこの欄があれば、`ai-check-lines.md` に従って、各コマンドに番号を入れる
