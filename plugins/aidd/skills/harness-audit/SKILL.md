# ハーネス監査（harness-audit）

リポジトリのファイルが、そのリポジトリの規約・方針・価値に合うかと、ファイル間の整合性を監査する。監査の本体は Workflow の `harness-audit-run` で、このスキルはその入口になる。実行前に見込みを示して続けるかを聞くのは、Workflow からは利用者に質問できないため。

検出とレポートだけを行い、ファイルは直さない。リンク切れ・markdown 規約などの機械チェックは Lint の担当で、この監査は扱わない。

## 参照ファイル

| ファイル | 役割 |
| --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/workflows/harness-audit-run.js` | 監査の本体。段ごとのモデルと effort は、冒頭の `MODELS` が正典 |

## 何を見るか

| 観点 | 中身 |
| --- | --- |
| 規約違反 | 各ファイルが、当てはまる規約・方針に反していないか |
| 価値に反する | 各ファイルが、価値・原則（`docs/values` など）に反していないか。解釈を含むため、価値の文を引用して示す |
| 値の矛盾 | 同じことについて、ファイルごとに違う値が書かれていないか。コードのコメント・設定値とドキュメントの食い違いも含む |
| 重複記述 | 同じ手順・設定値が、唯一の情報源以外にも書かれていないか |
| 参照方向違反 | ドキュメントの層から上の層を参照していないか（参照方向の規約があるリポジトリだけ） |

規約は、実行するたびに対象のリポジトリから探す（`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`・docs の方針・価値など）。規約が無いリポジトリでは、値の矛盾だけを見る。

## 手順

### Step 1: 対象を列挙する

リポジトリのルートで、追跡中のテキストファイルを列挙する。引数があれば、`git ls-files` の後ろにそのパスを並べて絞る。

```bash
git ls-files -- <引数のパス（無ければ省く）> \
  | grep -vE '(^|/)(node_modules|vendor|dist|build|tmp)/' \
  | grep -viE '\.(png|jpe?g|gif|ico|svg|webp|bmp|pdf|zip|gz|tar|tgz|woff2?|ttf|otf|eot|mp3|mp4|mov|webm|map)$|\.min\.(js|css)$|(^|/)(package-lock\.json|pnpm-lock\.yaml|[^/]*\.lock)$'
```

- 依存・生成物・`tmp/`・画像などのバイナリ・lock ファイルを除く。人が書いたテキストではなく、規約を当てても意味が無いため
- 0 件なら、その旨を伝えて終わる

### Step 2: 見込みを出す

Step 1 の一覧から、次を数える。トークン数は事前に分からないため、件数・総量・エージェント数で示す。

- 件数：全部と、markdown（`.md`）だけの 2 通り
- 総量：行数と KB（`wc -lc` で数える）
- エージェント数：下の表の形で示す。モデルと effort は、参照ファイルの `MODELS` を読んで書く

| 段 | エージェント数 |
| --- | --- |
| Rubric（規約をチェックリストにする） | 1 |
| Inspect（各ファイルの検査） | ファイル数 |
| Verify（ファイルごと） | 0〜ファイル数（違反の候補があるファイルの数） |
| Detect（横断の突合） | 1 |
| Verify（横断） | 横断の候補の数（Detect が終わるまで分からない） |
| Report | 1 |

最小はファイル数 + 3 体、最大は「ファイル数 × 2 + 3 + 横断の候補の数」体になることを添える。

### Step 3: 続けるかを聞く

見込みを示し、`AskUserQuestion` で次から選んでもらう。

| 選択肢 | 次の動き |
| --- | --- |
| 全部（N 件） | Step 1 の一覧のまま Step 4 へ |
| markdown だけ（M 件） | 一覧を `.md` だけにして Step 4 へ |
| 絞る | 上位のディレクトリごとの件数を示し、対象のパスを聞く。絞った一覧で Step 2 からやり直す |
| 中止 | 何もせずに終わる |

- 件数が 100 を超えたら、「絞る」を先頭に置き、ラベルに「(Recommended)」を付ける。100 以下なら「全部」に付ける。100 を超えると、横断の突合で 1 体が読む事実集合が大きくなるため
- 「絞る」には、分けて実行すると、グループをまたぐ矛盾は見つからないことを説明に添える
- 件数が 450 を超えたら、「全部」は出さない。Workflow のエージェント数の上限（1,000）に当たるため、Workflow 側でも止まる

### Step 4: Workflow を呼ぶ

Workflow ツールで、`name` に `aidd:harness-audit-run`、`args` に対象の一覧を渡して呼ぶ。`args` は JSON の値のまま渡す（文字列にしない）。

```json
{ "files": ["README.md", "docs/README.md"] }
```

- 名前で呼べなければ、`scriptPath` に `${CLAUDE_PLUGIN_ROOT}/workflows/harness-audit-run.js` を渡して呼ぶ
- どちらでも呼べなければ、エラーを伝えて終わる
- 実行の前に、Workflow の許可プロンプトが出る。`allowed-tools` に `Workflow` を入れていないため

### Step 5: 報告する

Workflow の戻り値から、次を伝えて終わる。

- レポートのパス（`tmp/<ブランチ名>/harness-audit_<yyyymmdd_hhmmss>.md`。ブランチ名の `/` は `-` に置き換える。規約は `aidd` の `README.md` の「ブランチ名の `/` は `-` に置き換える」）
- 監査したファイル数・確定した指摘の数・指摘の候補の数
- 当てはまる規約が無かったファイルの数（0 でなければ）

## 使用する引数

`$ARGUMENTS` は、対象を絞るパス（空白区切り）。省くと、追跡中の全テキストファイルが対象になる。

## 禁止事項

- ❌ 見込みを示して聞かずに、Workflow を呼ぶ
- ❌ 利用者に伝えずに、対象を減らす（除いたファイル・当てはまる規約が無いファイルは件数を示す）
- ❌ 監査の結果を受けて、対象のファイルを直す（レポートの出力だけにとどめる）
- ❌ このリポジトリに無い規約を根拠に指摘する
