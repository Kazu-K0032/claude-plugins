# CLAUDE.md

このファイルは、このリポジトリ内のコードを扱う際に、Claude Code (claude.ai/code) にガイダンスを提供するものです。

## 絶対禁止

例外なく守る。違反は即アウトで、判断の余地はない。

- SSOT を破る重複記述をしない。唯一の情報源にリンクで紐づける
- 未読の既存ファイルに Write しない
- データ消失・課金影響・履歴破壊を伴う操作を無断実行しない
- ドキュメントを無断で自動編集しない。提案にとどめる（条件は「ドキュメント更新を提案するとき」を参照）
- 未検証のパッケージ版・Docker イメージタグ・クラウド設定値を「確認済み」と断定しない

## 手順ルール

行為自体は許可される。やる前に必ず次を踏む。

### 破壊的操作の前

データ消失・課金影響・履歴破壊を伴う操作（検出対象は [`guard-destructive.sh`](.claude/hooks/guard-destructive.sh) の `patterns` を正典とする）を実行する前に、次を踏む。

- 削除・変更される対象を列挙する
- 対象が実データ（本番環境・データベース・tfstate・アップロード済みメディア等）を含まないか点検し、含む場合は明示承認を待つ
- 復元不可の削除（スナップショット無しのインスタンス削除等）は、バックアップ取得の要否を先に確認する
- IaC 統合・リソース再作成は、既存リソースに `import` を伴うか確認し、ステートフルなリソースの replace を避ける
- 例示値・プレースホルダ ID（レコード ID・リソース ID 等）をそのまま実行しない。破壊的コマンドは対象の実 ID を確認してから実行する

### ファイル編集の前

- 既存の可能性があるファイルは必ず Read してから書く
- 複数ファイルを編集する前に、どのファイルをなぜ変更するかを述べる。実装ファイルとテストファイルを取り違えない

### 大規模ランの前

監査・移行・多数ファイル修正など、1 セッションで終わらない規模の作業を始める前に、次を踏む。

- 最初からスコープを分割し、1 セッションで完了できる単位に収める
- 長い操作の前にステップ化し、進捗を `tmp/` のチェックポイントに残す。セッションが中断しても次セッションが再開できる状態を保つ

### ドキュメント更新を提案するとき

- 今回の変更が触ったコード/インフラと、既存ドキュメントの記述が食い違うとき
- ユーザーの指示が既存の禁止事項と矛盾するとき、または新しい恒久ルールとして残すべき指示があったとき
- README.md / CLAUDE.md / docs/ の SSOT が崩れる変更を加えたとき

### 「反映されない」と判断する前

- 「変更が効かない／反映されない」と診断する前に、編集したファイルが実際に配信・マウントされている実体と一致するか確認する
- TODO: このリポジトリ固有の配信経路（Docker のマウント元・ビルド成果物の出力先・有効なテーマ／プラグイン等）を列挙する
- ブラウザキャッシュ／CDN を疑う前に、上記のローカル配信経路の一致を先に潰す

### 事実を確認できないとき

- 公式レジストリ／ドキュメントで確認できない場合は、その旨を明示する
- URL・パッケージ版・リリース情報は記憶で書かず、一次情報／公式リリースページで裏取りしてから引用する

## リポジトリガイド

### ドキュメント構成

- `README.md` は **全ドキュメントへのリンクを集約するエントリポイント**として扱う。新しい文書を追加したら README.md と `docs/README.md` のリンクを更新する
- `docs/` 配下は文書の性格でディレクトリを分け、各ディレクトリの `README.md` を案内板として運用する
- 文書の振り分けルール
  - `docs/specs/` — 何を作るか（機能要件・非機能要件・スコープ）
  - `docs/architecture/` — どう作るか（システム構成・全体像）
  - `docs/strategies/` — どう進めるか（開発・テストの方針）
  - `docs/adr/` — なぜその選択をしたか（個別判断、1 判断 = 1 ファイル）
  - `docs/runbook/` — 実作業の手順（環境構築・デプロイ・運用）
  - `docs/log/` — 実作業の経緯（時系列の作業ログ。手順そのものは runbook が SSOT）
  - `docs/knowledge/` — ツール・プラグインの入門知識（1 ツール 1 ファイル。前提知識なしで読める共有ドキュメント）

### `.claude/` ファイルのメタデータ規約

Rules・Skills（`SKILL.md`）の frontmatter には `docs-type` を必ず指定する。ファイルを作成・更新する場合は、タグの値を考慮して記載する事。

指定されていない場合や新規で Rules・Skills を作成する場合は、どのタイプに属するかを問いかける事。

| 値 | 意味 |
| --- | --- |
| `people-doc` | 人が読む用。AI に読ませることは考えていない（または考えずに記載してよい）。チーム全体が理解しやすい文章および文章量を意識する |
| `ai-doc` | AI が読む用。人に読ませることは考えていない（人にとって理解しにくい構成でも想定内）。LLM がブレずにルールを理解することを優先する |
| `people-ai-doc` | 人も AI も読む想定。LLM の特性に合わせて書くが、人が読むために冗長な記述も許容する |

- 人が読む文書: チーム全体が理解しやすい文章であること。文章量が少なく、ストレスなく読めること。結論ベースの文章であること。出典や引用を添えて信頼性の高い文書にすること
- AI が読む文書: LLM が同じルールを参照してもブレずに動作できること。LLM が持つ問題（ハルシネーション・Lost in the middle）を解消する構成であること。Claude Code 公式の仕様やベストプラクティスに沿っていること。AI がルールを守る上で必要な情報だけに限定すること
- AI と人が読む文書: 基本は「AI が読む文書」を守るが、人が読む上で理解しやすく納得感を持たせることも考慮する事。参考リンクの付与や、ルール（What）だけでなくルールに対する理由（Why）を適度に添えること
