# ドキュメント追従チェック（docs-sync）

今のブランチの差分（コード・インフラ・md）を分析し、変更に追従して更新すべき md ドキュメントを特定して、レポートに書く。検出と提案だけを行い、ドキュメントは直さない。

- 外へ書き込むもの：`tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` のレポート
- 人がすること：レポートを読み、ドキュメントを直すかを決める

## 参照ファイル

| ファイル | いつ読むか |
| --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/references/base-branch.md` | 手順 1 で、比べるブランチを決めるとき |
| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/scripts/run-checks.sh` | 手順 2 で実行する（差分の列挙・機械チェック） |
| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/errors.md` | 手順 2 でスクリプトが `STOP`・`ERROR` を返したとき、終了コードの意味を確かめるとき |
| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/docdd-design.md` | 手順 2 の出力を読むとき、手順 3 で追従を判定するとき、手順 4 で重さを分けるとき（役割分担・チェック対象・判定範囲・重大度） |
| `${CLAUDE_PLUGIN_ROOT}/references/document.md` | 手順 3 で追従を判定するとき（重複排除（SSOT）・文体・構造のルール） |
| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/output-template.md` | 手順 4 でレポートを書くとき |
| `${CLAUDE_PLUGIN_ROOT}/references/markdown.md` | 手順 4 でレポートを書くとき（markdown の書式） |

## 想定している引数

引数は受け取らない。比べるブランチは手順 1 で決め、スクリプトが対象の差分を列挙する。

## 出力先

`tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に書く。ブランチ名は `git branch --show-current` で取り、`/` は `-` に置き換える（規約は `aidd` の `README.md` の「ブランチ名の `/` は `-` に置き換える」）。タイムスタンプは `date +%Y%m%d_%H%M%S` で取る。

## 手順

### 1. 比べるブランチを決める

`base-branch.md` の「規約を探す」「今のブランチのマージ先を決める」「比べる先を最新にする」で、今のブランチのマージ先を決める。PR も規約も無ければ、`--base` を付けずに手順 2 へ進む（スクリプトが既定ブランチ（`origin/HEAD`）と比べる）。決めたブランチと根拠（PR のマージ先・規約のファイル・既定ブランチ）は、手順 4 のレポートに書くため控えておく。

### 2. 差分を列挙し、機械チェックを実行する

リポジトリのルートで次を実行し、標準出力を保持する。スクリプトは `git`・`bash`・`perl`・`awk` を使う。`<比べるブランチ>` は手順 1 で決めたもの（通常は `origin/<マージ先>`）で、決まらなければ `--base` を付けない。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/scripts/run-checks.sh" --base "<比べるブランチ>"
```

`STOP`・`ERROR` が出たら、`errors.md` に従って終わる。出力の中身は `docdd-design.md` の「スクリプトの出力」にある。`SKIP` は異常ではないため FAIL に数えず、レポートには「対象外」と書く。

### 3. 追従が要るかを判定する

「変更された非 md」のファイルを Read・`git diff` で確かめ、`docdd-design.md` の「追従判定範囲」に従って判定する。判定の前に、「依拠する外部ルール」にあるこのリポジトリの規約を Glob・Grep で探す。パスはリポジトリごとに違うため固定しない。見つからない観点は一般的なベストプラクティスで判定し、規約違反としては挙げない。

1. 変更されたコード・インフラが、既存の md の記述と食い違っていないか
1. 食い違う場合、どの md を・どう更新すべきか（対応表があれば、唯一の情報源に当たるファイルを優先して特定する）
1. 変更した md 自体が、関連するほかの md（索引のリンク・参照先）との整合を崩していないか
1. 追従すべきなのに更新していない md（ドリフト）を、重大度を付けて挙げる

変更した md の機械チェックは手順 2 のスクリプトが済ませているため、ここでは重ねて点検しない。

### 4. レポートを書く

`output-template.md` に従い、手順 2 のスクリプトの出力と手順 3 の判定を合わせて書き、出力パスをユーザーに伝える。

- 機械チェックの FAIL と手順 3 の指摘を合わせ、`docdd-design.md` の「重大度」に従って high・medium・low に分ける。総合判定（PASS / FAIL）は出さない。スクリプトの終了コードだけで指摘の有無を決めない
- 冒頭の文に、手順 2 の基準ブランチと変更ファイル数を入れる
- 手順 1 で決めた根拠と、`git fetch` を断られたときはその旨を、冒頭の文の直後に注記で書く。比べる先を取り違えていないかを、読み手が確かめられるようにするため
- `SKIP` にした項目と、手順 3 で参照した規約も、同じ注記に書く。PASS は書かない
- 推奨アクションに、直す順の番号付きの一覧（最大 5 件）を書く

## 禁止事項

- ❌ 基準ブランチでフローを続ける（必ず停止する）
- ❌ 手順 1 で PR・規約を確かめずに、既定ブランチと比べる
- ❌ 検出した問題を自動で直す（レポートの出力だけにとどめる）
- ❌ 機械チェック（手順 2）の判定範囲を、手順 3 の判定で重ねて点検する（役割分担を崩さない）
- ❌ `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` 以外のファイルを書き換える
- ❌ 手順 2 が FAIL でも手順 3 を省く（停止時を除き、必ず両方を行って合わせる）
- ❌ `SKIP` を FAIL として報告する
- ❌ このリポジトリに存在しない規約を根拠に指摘する

## 保守

- リポジトリ全体の規約への適合と、横断的な重複記述・値の矛盾を網羅して監査するのは `/aidd:harness-audit`（差分ではなく全ファイルが対象）。このスキルは「このブランチの変更にドキュメントが追従しているか」に特化する
- `allowed-tools` に `run-checks.sh` の `Bash` パターンを含めていない。プラグインの実体パスは `${CLAUDE_PLUGIN_ROOT}` で解決するが、この変数が `allowed-tools` の frontmatter で展開されるかは公式に記載がないため、当てにせず通常の許可プロンプトを通す
