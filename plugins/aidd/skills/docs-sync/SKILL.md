# ドキュメント追従チェック（docs-sync）

現在のブランチの差分（コード・インフラ・md）を分析し、**変更に追従して更新すべき md ドキュメントを特定**して `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に出力する。検出と提案のみで、ドキュメントの自動修正は行わない。

- 外へ書き込むもの：`tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md`（レポート）
- 人がすること：レポートの指摘を読み、ドキュメントを直すかを決めて直す

## 参照ファイル

| ファイル | いつ読むか |
| --- | --- |

| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/docdd-design.md` | 手順 3 で追従の要否を判定するとき（チェック対象・判定範囲）と、手順 4 で重大度を分けるとき。役割分担・リンク検査から外すファイル・`/aidd:harness-audit` との補完関係もここ |
| `${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/output-template.md` | 手順 4 で、レポートを書くとき |
| `${CLAUDE_PLUGIN_ROOT}/references/merge-target.md` | 手順 1 で、比べるブランチ（マージ先）を決めるとき |
| `${CLAUDE_PLUGIN_ROOT}/references/report-format.md` | 手順 4 で、レポートの見出しの構成・推奨アクションを書くとき |

| `${CLAUDE_PLUGIN_ROOT}/references/markdown.md` | 手順 3 で、markdown 書式規約を当てるとき |

## 想定している引数

引数は受け取らない。比べるブランチは手順 1 で決め、スクリプトが対象差分を列挙する。

## 出力先

`tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に書く。取り方と書き方は手順 4、中身の構成は `output-template.md` にある。

## 手順

次を満たす場所で実行する。

- リポジトリのルートで実行されること
- `git` / `bash` / `perl` / `awk` が利用可能であること
- マージ先がある（基準ブランチ以外の）ブランチであること

### 1. 比べるブランチを決める

`git branch --show-current` で今のブランチを取り、そのマージ先を `merge-target.md` の順で決める。

- 基準ブランチは、今のブランチのマージ先にする。既定ブランチに決め打ちしない
- PR も規約も無ければ、`--base` を付けずに手順 2 へ進む。スクリプトが既定ブランチ（`origin/HEAD`）と比べる
- `git fetch` を断られたときの古い可能性と、決めたブランチの根拠は、手順 4 のレポートに書く

### 2. 差分を列挙し、機械チェックを実行する

次のコマンドを実行し、標準出力を保持する。`<比べるブランチ>` は手順 1 で決めたもの（通常は `origin/<マージ先>`）。手順 1 で決まらなければ `--base` を付けない。

```bash
bash "${CLAUDE_PLUGIN_ROOT}/skills/docs-sync/scripts/run-checks.sh" --base "<比べるブランチ>"
```

スクリプトは以下を出力する。

- 基準ブランチ上の場合は `STOP` と表示し終了コード 3。**この場合は以降を実施せず、停止理由をユーザーに伝えて終了する**
- `--base` のブランチが見つからない場合は `ERROR` と表示し終了コード 2。**以降を実施せず、渡したブランチと原因をユーザーに伝えて終了する**
- 基準ブランチ（決め方を括弧で添える）・変更ファイル総数
- 「## 変更された md」「## 変更された非 md（docs 追従判断の入力）」のファイル一覧
- 変更 md に対する「相対リンク切れ」「markdown 規約」の PASS/FAIL
- 全走査（差分非依存）の「全 docs リンク切れ」「SSOT 一覧ポインタ存在」の PASS/FAIL
- リンク検査から外したファイルの件数（外したときだけ。指定のしかたは `docdd-design.md` の「リンク検査から外すファイル」）
- 「## サマリ」配下に各カテゴリの FAIL 件数（レポートの材料。レポートの構成とは別で、レポートにサマリの節は作らない）

終了コードは、機械チェック FAIL があれば `1`、`ERROR`（`--base` のブランチが無いなど）なら `2`、基準ブランチでの停止なら `3`、すべて PASS なら `0`。

基準ブランチは、今のブランチのマージ先（決め方は手順 1）。マージ先が今のブランチ自身になるとき（既定ブランチで実行したときなど）と、`main` / `master` では差分の基準が無いため**フローを停止する**。`run-checks.sh` が `STOP` を返したら、その旨をユーザーに伝えて終了する（レポートは作らない）。

`develop` のように、ほかのブランチのマージ先になるブランチでも、自分のマージ先（`stg`・`main` など）があれば止めない。リリース前に、未リリースの変更へドキュメントが追従しているかを点検できるようにするため。

**`SKIP` の扱い**: `SSOT 一覧ポインタ` は、そのリポジトリが該当の規約を使っていない場合 `SKIP` を返す。これは異常ではないため FAIL として扱わず、レポートには「対象外」と記す。

### 3. 追従要否を判定する

スクリプトが出力した「変更された非 md」のファイル群を `Read` / `git diff` で確認し、`docdd-design.md` の「追従判定範囲」に従って次を判定する。

判定の前に、**このリポジトリの規約を Glob / Grep で探す**（パスはリポジトリごとに違うため固定しない）。

- ドキュメント更新の判断軸・情報と唯一の情報源の対応表: `CLAUDE.md`・`docs/README.md`・`AGENTS.md` 等
- ドキュメント階層の責務・参照方向の規約: `.claude/rules/*.md`・`docs/strategies/*.md`・`CONTRIBUTING.md` 等

見つからない観点は、一般的なベストプラクティスで判定し**規約違反としては挙げない**。

判定内容:

1. 変更されたコード・インフラが、既存 md の記述と食い違っていないか
1. 食い違う場合、**どの md を・どう更新すべきか**（対応表があれば唯一の情報源に該当するファイルを優先的に特定）
1. 変更 md 自体が、関連する他の md（索引のリンク・参照先）との整合を崩していないか
1. 追従すべきだが未更新の md（ドリフト）を重大度付きで列挙する

変更 md の機械チェックは手順 2 のスクリプトで検出済みのため LLM では重複点検しない。

### 4. レポートを出力する

1. `git branch --show-current` で現在のブランチ名を取得する（出力パス用。`/` は `-` に置換する。規約は `aidd` の `README.md` の「ブランチ名の `/` は `-` に置き換える」）
1. `date +%Y%m%d_%H%M%S` でタイムスタンプを取得する
1. `output-template.md` のテンプレートに従い、手順 2 のスクリプト出力と手順 3 の判定結果を統合して `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に書き込み、出力パスをユーザーに報告する
   - 機械チェックの FAIL と手順 3 の指摘を、`docdd-design.md` の「重大度」に従って high・medium・low に分ける
   - 冒頭の文に、手順 2 の基準ブランチと変更ファイル数を入れる
   - 手順 1 で決めた根拠（PR のマージ先・規約のファイル・既定ブランチ）と、`git fetch` を断られたときはその旨を、冒頭の文の直後に注記で書く。比べる先を取り違えていないかを、読み手が確かめられるようにするため
   - `SKIP` にした項目と、手順 3 で参照した規約も、同じ注記に書く。PASS は書かない
   - 推奨アクションは `report-format.md` の決まりで書く

レポートを書くときは、次の決まりに従う。

- 機械チェック（手順 2）の FAIL と追従判定（手順 3）の指摘を合算し、high・medium・low に分ける。総合判定（PASS / FAIL）は出さない
- スクリプトの終了コードのみで指摘の有無を決めず、手順 3 の LLM 判定結果を必ず合算する
- `SKIP` は FAIL に数えない（規約を使っていないリポジトリの正常状態）
- レポートは `tmp/` 配下に書き込むのみで、検出した問題の自動修正は行わない

## 禁止事項

- ❌ 基準ブランチでフローを継続する（必ず停止する）
- ❌ 手順 1 で PR・規約を確かめずに、既定ブランチと比べる
- ❌ 検出した問題を自動修正する（レポート出力のみに留める）
- ❌ 機械チェック（手順 2）の判定範囲を LLM 判定（手順 3）で重複点検する（`docdd-design.md` の役割分担を崩さない）
- ❌ `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` 以外のファイルを書き換える
- ❌ 手順 2 が FAIL でも手順 3 を省略する（停止時を除き、必ず両方実施して合算）
- ❌ `SKIP` を FAIL として報告する
- ❌ このリポジトリに存在しない規約を根拠に指摘する

## 保守

`allowed-tools` に `run-checks.sh` の `Bash` パターンを含めていない。プラグインの実体パスは `${CLAUDE_PLUGIN_ROOT}` で解決するが、この変数が `allowed-tools` の frontmatter で展開されるかは公式に記載がないため、当てにせず通常の許可プロンプトを通す。
