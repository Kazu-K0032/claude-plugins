# 出力テンプレート

`docs-sync` Skill が `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に書き出すレポートの、`docs-sync` 固有の中身を定義する。見出しの構成・「なし」の書き方・推奨アクションの決まりは、`pr-review`・`harness-audit` と共通の `references/report-format.md` に従う。

````markdown
# docs-sync 実行結果

本ドキュメントは、docs-sync によって、ブランチの変更にドキュメントが追従しているかの観点から、<基準ブランチ> との差分（変更 <総数> ファイル：md <件数> / 非 md <件数>）に問題が無いかチェックし結果をレポートしたものです。

> 比べたブランチ：`<基準ブランチ>`（<決めた根拠：PR のマージ先 / 規約のファイル / 既定ブランチ>。`git fetch` を断られたときは「手元の版で比べたため、古い可能性がある」と添える）
>
> 対象外：<SKIP になった項目と理由。無ければこの行を書かない>
>
> 参照した規約：`<探索で見つかった規約ファイル。無ければ「なし（一般的なベストプラクティスで判定）」>`

## high

- 対象 md: `<更新すべき docs>`
  - トリガー変更: `<変更された非 md ファイル>`
  - 不整合: `<実装と docs の食い違い>`
  - 推奨更新: `<どこを・どう直すか>`
- 対象 md: `<file>:<line>`
  - 検出: 機械チェック（<項目名>）
  - 不整合: <内容>
  - 推奨更新: <どう直すか>

## medium

なし

## low

なし

## 推奨アクション

1. `<ファイルのパス>` <何を直すか>
````

## 書き方のルール

- 機械チェックの FAIL は、`docdd-design.md` の「重大度」の表のとおりに high・medium・low へ入れる。追従判定の指摘は、同じ表の基準で重さを決める
- 機械チェックの指摘は、「トリガー変更」の行を「検出」の行に替えて書く
- 機械チェックの PASS は書かない。指摘が無ければ、問題が無いと分かるため
- 注記の「比べたブランチ」は必ず書く。根拠は `SKILL.md` の手順 1 で決めたもの（規約から決めたときは、そのファイルのパス）を書く
- `SKIP` を返した項目は、注記の「対象外」に書き、括弧内に理由を添える。**FAIL として書かない**
- 注記の「参照した規約」は、追従判定で探索して見つかった規約ファイルを列挙する。規約が無いまま「規約違反」と書かない
