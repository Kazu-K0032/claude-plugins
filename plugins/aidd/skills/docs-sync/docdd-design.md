## 役割分担

| フェーズ | 担当 | 対象 |
| --- | --- | --- |
| 比べるブランチの決定 | LLM | PR・規約から、今のブランチのマージ先を決めて `run-checks.sh` に渡す |
| 差分列挙・機械チェック | `run-checks.sh` | ブランチ差分の列挙・変更 md の相対リンク切れ・markdown 規約、および全 md のリンク切れ・SSOT 一覧ポインタ（全走査・差分非依存） |
| 追従要否の判定 | LLM | 非 md 変更（コード・インフラ）に追従して更新すべき md の特定・更新提案 |
| レポート出力 | LLM | スクリプト出力と LLM 判定を統合して `tmp/<ブランチ名>/docs-sync_<yyyymmdd_hhmmss>.md` に整形 |

## チェック対象

- 現在のブランチと基準ブランチの **merge-base 以降の差分**
- 基準ブランチは、今のブランチのマージ先。`SKILL.md` の手順 1 で決め（決め方の正典は `references/merge-target.md`）、`run-checks.sh --base` で渡す
- `--base` が無いときの解決順は `origin/HEAD`（リモートの既定ブランチ）→ `origin/main` → `main` → `origin/master` → `master` → `origin/develop` → `develop`
- 差分は「コミット済み＋作業ツリーの変更」を含む
- 差分ファイルを 2 つに分ける
  - **変更された md**: 機械チェックの対象
  - **変更された非 md（コード・インフラ）**: 追従判定（LLM）の入力

基準ブランチ上（マージ先が今のブランチ自身になるとき）と `main`・`master` では、差分の基準が無いため**停止する**（検出も提案も行わない）。`develop` など、ほかのブランチのマージ先でも、自分のマージ先があれば止めない。

### 評価対象外

- 差分に含まれないファイル（変更していない md・コードは対象外）。ただし全走査チェック（全 docs リンク切れ・SSOT 一覧ポインタ存在）は差分外の既存 md も対象とする
- `.gitignore` 対象ファイル（`git diff` が返さない）
- `node_modules` / `vendor` / `dist` / `build` / `tmp` 配下
- リポジトリ側で、リンク検査から外すと指定したファイル（リンク検査だけ。「リンク検査から外すファイル」を参照）

## 依拠する外部ルール

| ルール領域 | 参照先 |
| --- | --- |
| markdown 規約 | プラグインの `references/markdown.md` |
| 重複排除（SSOT）・文体・構造 | プラグインの `references/document.md` |
| ドキュメント更新の判断軸・情報と唯一の情報源の対応表 | **リポジトリ側を探索**（`CLAUDE.md`・`docs/README.md`・`AGENTS.md` 等） |
| ドキュメント階層の責務・参照方向 | **リポジトリ側を探索**（`.claude/rules/*.md`・`docs/strategies/*.md`・`CONTRIBUTING.md` 等） |

前 2 つはプラグインが同梱する共通規約。後 2 つはリポジトリごとに置き場所が違うため、パスを固定せず探索する。**見つからない観点は規約違反として指摘しない。**

外部ルールの内容を本ファイルに複製しない。本ファイルでは「どのルールを根拠にするか」のみを宣言する。

## 機械チェック範囲

対象は差分に含まれる md のみ。さらに種別でスコープを分ける。

- 相対リンク切れ・markdown 規約: 散文 md のみ。判定パターンは `docs/` `doc/` `documentation/` 配下、および任意階層の `README` / `CLAUDE` / `CONTRIBUTING` / `AGENTS`。`.claude/**` の SKILL.md 等はネストしたコードフェンスやリンク記法の例を含み誤検出するため対象外。相対リンク切れは、リンク検査から外すと指定したファイルも除く

次の 2 つは差分ではなく**リポジトリ全体**を対象にする。既存ファイルの壊れた参照は差分に現れず、差分スコープでは取りこぼすため。

- 全 docs リンク切れ（全走査）: 全散文 md（リンク検査から外すと指定したファイルを除く）の `](path)` リンク先存在
- SSOT 一覧ポインタ存在（全走査）: 「唯一の情報源」列を持つテーブルが指すパスの存在。インラインコードで書かれ `](path)` リンク記法に出ないため、リンク切れチェックとは別に検査する

### リンク検査から外すファイル

リポジトリ直下の `.docs-sync-link-ignore` に書いたパターンに当たるファイルは、2 つのリンク検査（相対リンク切れ・全 docs リンク切れ）の対象から外す。

- 書式は `.gitignore` と同じ（`#` で始まる行はコメント、末尾の `/` はディレクトリ）
- ファイルが無ければ、何も外さない
- 使いどころは、導入先のリポジトリを基準にリンクを書いたテンプレートなど、そのリポジトリの中では解決できないファイル
- markdown 規約からは外さない。テンプレートの書式の崩れは、導入先へそのまま配られるため

### リポジトリごとに検査するかを切り替える項目

SSOT 一覧ポインタ存在は、`CLAUDE.md`・`docs/README.md`・`README.md`・`AGENTS.md` のいずれにも「唯一の情報源」または「SSOT」列を持つテーブルが無いリポジトリでは `SKIP` を返す。使っていない規約で FAIL を出さないための措置。**`SKIP` は FAIL に数えない。**

### 相対リンク切れ

- `](path)` 形式リンクを抽出する
- `http://` / `https://` / `mailto:` で始まるもの・アンカー単独（`#xxx`）はスキップする
- 相対パスは存在確認する（アンカー付きはファイル存在のみ確認）

### SSOT 一覧ポインタ存在

- 「唯一の情報源」列を持つテーブルの各行から、最後に出てくるインラインコードをパスとして取り出す
- `/<plugin>:<skill>` 形式のスラッシュコマンドと、`http://` / `https://` / `mailto:` で始まるものは、パスではないためスキップする。名前空間の無い `/xxx` はパスと区別できないため存在確認する
- パスはリポジトリ直下を起点に存在確認する（アンカー付きはファイル存在のみ確認）

### markdown 規約チェック

[Markdownlint](https://github.com/DavidAnson/markdownlint) を元に、誤りが多発する次を優先検査する。

- MD025（H1 複数）/ MD040（コードフェンス言語）/ MD012（連続空行）/ MD047（末尾改行）

## 追従判定範囲（LLM・変更された非 md を入力に）

**コード・インフラの変更に md が追従できているか**が主眼。リポジトリ側の規約（対応表・参照方向）を探索し、見つかったものに照らして判定する。

### コード／インフラ変更への追従漏れ

変更された非 md が、既存 md の記述と食い違っていないか。食い違う場合、対応表があれば唯一の情報源に該当する md を特定し、どう更新すべきかを示す。

検査対象の対応例（リポジトリの構成に読み替える）:

| 変更されたもの | 追従を確認する md の例 |
| --- | --- |
| データモデル・ルーティング・テンプレートの対応 | アーキテクチャ文書 |
| 機能・URL・スコープ | 仕様書・要件定義 |
| コマンド・手順 | 手順書（runbook / セットアップ） |
| インフラ構成（IaC） | アーキテクチャ文書・インフラ手順書 |
| ディレクトリ構成 | ディレクトリ構造を記した文書（`CLAUDE.md` 等） |
| CI/CD 設定 | CI/CD 構成の文書 |

### 変更 md と関連 md の整合

変更した md が、索引のリンク一覧・参照先・唯一の情報源の一意性を崩していないか。新規 md を追加したのに索引から未リンク、などを検出する。

## 重大度

機械チェックの FAIL と追従判定の指摘を、同じ 3 段階に分ける。

- high: 実害・誤誘導（手順やコマンドが実装と食い違い、従うと失敗する）
- medium: 保守性低下（記述の陳腐化・唯一の情報源のドリフト）
- low: 軽微（表記ゆれ・補足不足）

### 機械チェックの重さ

機械チェックの FAIL は、種類で重さを固定する。

| 機械チェック | 重さ | 理由 |
| --- | --- | --- |
| 相対リンク切れ（変更 md）・全 docs リンク切れ（全走査） | high | 読み手が参照先にたどり着けず、手順を進められない |
| SSOT 一覧ポインタ存在（全走査） | medium | 唯一の情報源の記述が実体とずれ、保守性が下がる |
| markdown 規約 | low | 書式の崩れにとどまり、読めなくなる実害は小さい |

## 指摘の扱い

- 基準ブランチと `main`・`master` では停止（`STOP`）。レポートは作らない
- 機械チェックの FAIL と追従判定（LLM）の指摘を合算し、重さごとに high・medium・low へ分ける。総合判定（PASS / FAIL）は出さない
- `SKIP` は指摘に数えない
- 外部 URL のリンク切れはスコープ外（ネットワークアクセスが必要なため）
- 検出と提案のみ行い、自動修正は実施しない

## 補完関係

- リポジトリ全体の規約への適合と、横断的な重複記述・値の矛盾を網羅監査するなら `/aidd:harness-audit` を使う（差分ではなく全ファイルが対象）
- 本 Skill は「このブランチの変更にドキュメントが追従しているか」に特化する
