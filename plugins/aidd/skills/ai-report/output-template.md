# ai-report 出力フォーマット

`analyze.py report` がレポート `your-ai-report-<yyyymmdd_hhmmss>.md` を生成する。定量セクション（ハイライト・トークン内訳・**コスト試算**・モデル別・アクティビティ・ツール/MCP・**会話密度**・各種テーブル）は analyze.py が生成・整形する。Claude が用意するのは定性パートのみ。

## 定性パート（Claude が執筆）

`.ai-report-qualitative.md` に次のブロックをマーカー付きで書く。`analyze.py report` がマーカーで抽出し、総評サマリを冒頭、トークン効率・コスト最適化と改善提案を末尾（定量セクションの後）へ挿入する。マーカーが無い場合は全文を改善提案へ流し込む。

書き方のルール（SUMMARY / PROMPTS ブロック共通）:

- レポートは単体で読まれる。プロンプトを番号（「プロンプト 7」等）で参照しない。必ず実際の文面を `「…」` で短く引用する。
- 各項目は PREP 法で書く。結論（何が良い / 課題か）→ 理由（なぜ効く / 問題か。プロンプトエンジニアリング・LLM 特性の観点）→ 例（プロンプトの引用）の順。1 項目 2〜3 文に収め、括弧の入れ子で詰め込まない。
- 評価軸はプロンプト単体の内容から問題解決アプローチの組み立て方まで。コンテキスト設計・曖昧さ回避・役割や前提の提示・期待値の明示・出力の検証など、PE / LLM 特性を理解できているかを見る。
- 改善策を出すときは、プロンプトの書き方だけでなく Claude Code の標準機能・設定で仕組み化できないかも 1 軸として検討する（詳細は後述の「改善提案の共通軸」）。

```markdown
<!-- SUMMARY -->
（総評サマリ）プロンプトの使い方の良い点・改善点を、上記ルールに従い箇条書きで簡潔に。作業内容そのものの要約は不要（定量セクションが担う）。
<!-- /SUMMARY -->

<!-- PROMPTS -->
（プロンプト改善提案）総評の各点を Before/After で具体化する。実際のプロンプトを引用する。
<!-- /PROMPTS -->

<!-- TOKEN_EFFICIENCY -->
（トークン効率・コスト最適化）コストを踏まえ、トークン（＝費用）を減らす観点で評価・提案する。下記ルールに従い箇条書きで。
<!-- /TOKEN_EFFICIENCY -->

<!-- WORKFLOW_EFFICIENCY -->
（完了時間・手戻り削減）意図しない実装のやり直しと往復回数を減らし、タスクを最短で正しく終える観点で評価・提案する。下記ルールに従い箇条書きで。
<!-- /WORKFLOW_EFFICIENCY -->

<!-- PROMOTION_REASONS -->
（昇格候補理由）下記「PROMOTION_REASONS ブロックの書き方」に従い、エージェント名ごとに 1 行で書く。
<!-- /PROMOTION_REASONS -->
```

### 改善提案の共通軸（PROMPTS / TOKEN_EFFICIENCY / WORKFLOW_EFFICIENCY 共通）

改善策を出す全ブロックで、次を必ず 1 つの軸として検討する。ユーザー側の工夫（プロンプトの書き方）だけで終わらせない。

- **Claude Code の標準機能・設定で仕組み化できないか**を毎回検討する。plan mode・custom skill・subagents・hooks・output styles・`settings.json` 等で、同じ課題を再発させない形にできないかを併せて提案する。
- 提案する機能の**現在仕様（機能の有無・オプション名・挙動）は憶測で書かず、技術調査（`research` skill / `aidd-research` エージェント）か公式ドキュメントで裏取りしてから書く**（プラグインの `references/ai-research.md` 準拠。実パスは `SKILL.md` の参照ファイル表を見る）。Claude Code は更新が速く、記憶ベースの機能説明は陳腐化しやすい。裏取りできなければ「未確認」と明示し、断定しない。
- 機能名には「何のための機能か」を一言添える（プラグインの `references/plain-language.md` 準拠）。

### TOKEN_EFFICIENCY ブロックの書き方

トークン消費（＝コスト）を減らす観点で評価・提案する。定量セクションの「コスト試算」「トークン内訳」「会話密度」「プロンプト傾向」を根拠に、次の3点を箇条書きで書く。

- **文章の簡略化余地**: typed プロンプト一覧を読み、冗長・重複・貼り過ぎ（長文チャット全文・他 AI 出力の丸貼り等）でトークンを増やしている箇所を、実際の文面を `「…」` で引用して指摘する。
- **聞き返し問題を標準機能で減らせるか**: 「会話密度」（セッション平均プロンプト数・極短プロンプト率）を根拠に、短い往復が多いなら Claude Code 標準機能（plan mode・`/compact`・`/clear` 運用・custom skills・subagents・hooks・output styles 等）で減らせないか評価する。機能の扱い（現在仕様の裏取り・機能名の補足）は「改善提案の共通軸」に従う。
- **さらに減らす具体策**: コスト試算の数値に触れて（Step 2 の出力をそのまま引用し推測で作らない）、費用対効果の高い削減策を提案する。キャッシュ効率が高い場合はその旨も添える。

制約:

- コスト・トークン数は必ず analyze.py 出力の数値を引用する。単価は推定であることを踏まえ、断定しすぎない。
- Claude が読めるのはユーザーのプロンプト（collect 出力）だけで、**assistant の出力本文は読めない**。出力の簡略化は output_tokens の量と一般則として述べ、具体文面を断定しない。

### WORKFLOW_EFFICIENCY ブロックの書き方

「トークン（費用）」ではなく「タスクを最短で正しく完了させる」観点で評価・提案する。TOKEN_EFFICIENCY と目的が違うため、費用の話は繰り返さない。定量セクションの「手戻りシグナル」「会話密度（聞き返し傾向）」「permissionMode 分布」を根拠に、次の 3 点を箇条書きで書く。

- **手戻りの実態**: 「手戻りシグナル」の検出数・率を引用し、該当プロンプトを `「…」` で引用する。確認不足で意図しない実装が生まれた疑いがあれば、着手前に不足していた前提（完成条件・対象ファイル・やらない範囲）を推定で述べる。assistant の出力本文は読めないため、原因は断定せず「〜の可能性」で書く。
- **聞き返し・往復の多さ**: 「会話密度」（セッション平均プロンプト数・極短プロンプト率）を根拠に、着手前の情報不足で往復が増えていないかを評価する。TOKEN_EFFICIENCY と同じ数値を使ってよいが、ここでは「時間・手戻り」の観点で述べる。
- **標準機能・設定での対策**: plan mode（着手前に方針を合意する）・custom skill（確認手順を定型化する）・hooks や settings（着手前チェックを自動化する）等で、手戻り・往復を減らせないか提案する。機能の扱い（現在仕様の裏取り・機能名の補足）は「改善提案の共通軸」に従う。

制約:

- 「手戻りシグナル」は保守的な語彙マッチで、誤検知・取りこぼしを含む。検出プロンプトを自分で読み、明らかな誤検知は除いてから引用する。数値は断定しすぎない。
- assistant の出力本文は読めない。手戻りの原因はユーザーの修正プロンプトからの推定に留め、Claude が何を間違えたかを断定しない。

### PROMOTION_REASONS ブロックの書き方

`collect` の stdout に出力される「昇格候補エージェント 関連プロンプト」セクションを読んで執筆する。

- 形式: `エージェント名: 理由テキスト`（1 エージェント 1 行）
- 理由は「〇〇を調べるときに毎回同じ観点で起動しているため。」のように、繰り返している用途を 1 文で書く
- 関連プロンプトは Agent ツールへ渡した指示文そのもの。空になることはほぼ無いが、空だった場合は「（関連プロンプトなし。名前からの推定）」と明記して書く
- エージェント名にコロン（`:`）が含まれる場合も `partition(":")` で最初のコロンで分割されるため問題ない
