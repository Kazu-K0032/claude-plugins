# ai-report 出力フォーマット

`analyze.py report` がレポート `your-ai-report-<YYYYMMDD-HHMMSS>.md` を生成する。定量セクション（ハイライト・**走査対象ログ（カバレッジ）**・トークン内訳・**コスト試算**（モデル別ターン数含む）・日別アクティビティ・**ターン所要時間**・ツール/MCP・**ツール失敗・権限拒否**（ツール × 事由・権限未許可で止まったサブコマンド・発生箇所（スキル帰属）と発生箇所ごとの内訳付き）・**検証コマンド**・**スキル別コスト帰属**・**コード変更量**・effort 分布・**会話密度**・**手戻りシグナル**（評価カラム付き）・**確認プロンプトの回答一貫性**・**定型パターン**・**蛇足行動**・各種テーブル）は analyze.py が生成・整形する。集計はサブエージェント・Workflow 実行分を含み、同一リポジトリの全クローン・worktree のログを走査する。Claude が用意するのは定性パートのみ。

## 定性パート（Claude が執筆）

`.ai-report-qualitative.md` に次のブロックをマーカー付きで書く。`analyze.py report` がマーカーで抽出し、総評サマリを冒頭、トークン効率・コスト最適化と改善提案を末尾（定量セクションの後）へ挿入する。マーカーが無い場合は全文を改善提案へ流し込む。

書き方のルール（SUMMARY / PROMPTS ブロック共通）:

- レポートは単体で読まれる。プロンプトを番号（「プロンプト 7」等）で参照しない。必ず実際の文面を `「…」` で短く引用する。
- 各項目は PREP 法で書く。結論（何が良い / 課題か）→ 理由（なぜ効く / 問題か。プロンプトエンジニアリング・LLM 特性の観点）→ 例（プロンプトの引用）の順。1 項目 2〜3 文に収め、括弧の入れ子で詰め込まない。
- 評価軸はプロンプト単体の内容から問題解決アプローチの組み立て方まで。コンテキスト設計・曖昧さ回避・役割や前提の提示・期待値の明示・出力の検証など、PE / LLM 特性を理解できているかを見る。
- 改善策を出すときは、プロンプトの書き方だけでなく Claude Code の標準機能・設定で仕組み化できないかも 1 軸として検討する（詳細は後述の「改善提案の共通軸」）。

```markdown
<!-- SUMMARY -->
（総評サマリ）プロンプトの使い方の良い点・改善点を、上記ルールに従い箇条書きで簡潔に。作業内容そのものの要約は不要（定量セクションが担う）。
<!-- /SUMMARY -->

<!-- PROMPTS -->
（プロンプト改善提案）総評の各点を Before/After で具体化する。実際のプロンプトを引用する。
<!-- /PROMPTS -->

<!-- TOKEN_EFFICIENCY -->
（トークン効率・コスト最適化）コストを踏まえ、トークン（＝費用）を減らす観点で評価・提案する。下記ルールに従い箇条書きで。
<!-- /TOKEN_EFFICIENCY -->

<!-- WORKFLOW_EFFICIENCY -->
（完了時間・手戻り削減）意図しない実装のやり直しと往復回数を減らし、タスクを最短で正しく終える観点で評価・提案する。下記ルールに従い箇条書きで。
<!-- /WORKFLOW_EFFICIENCY -->

<!-- MECHANIZATION -->
（ワークフローの仕組み化・短縮）行動パターンを標準機能で仕組み化し、品質を落とさず手数を減らす観点で評価・提案する。下記ルールに従い箇条書きで。
<!-- /MECHANIZATION -->

<!-- PROMOTION_REASONS -->
（昇格候補理由）下記「PROMOTION_REASONS ブロックの書き方」に従い、エージェント名ごとに 1 行で書く。
<!-- /PROMOTION_REASONS -->
```

### 改善提案の共通軸（PROMPTS / TOKEN_EFFICIENCY / WORKFLOW_EFFICIENCY / MECHANIZATION 共通）

改善策を出す全ブロックで、次を必ず 1 つの軸として検討する。ユーザー側の工夫（プロンプトの書き方）だけで終わらせない。

- **Claude Code の標準機能・設定で仕組み化できないか**を毎回検討する。plan mode・custom skill・subagents・hooks・output styles・`settings.json` 等で、同じ課題を再発させない形にできないかを併せて提案する。
- 提案する機能の**現在仕様（機能の有無・オプション名・挙動）は憶測で書かず、`aidd:research` サブエージェント（本プラグイン同梱）か公式ドキュメントで裏取りしてから書く**（プラグインの `references/ai-research.md` 準拠。実パスは `SKILL.md` の参照ファイル表を見る）。Claude Code は更新が速く、記憶ベースの機能説明は陳腐化しやすい。裏取りできなければ「未確認」と明示し、断定しない。
- 機能名には「何のための機能か」を一言添える（プラグインの `references/plain-language.md` 準拠）。

### TOKEN_EFFICIENCY ブロックの書き方

トークン消費（＝コスト）を減らす観点で評価・提案する。定量セクションの「コスト試算」「トークン内訳」「スキル別コスト帰属」「ツール失敗・権限拒否」「会話密度」「プロンプト傾向」を根拠に、次の4点を箇条書きで書く。

- **文章の簡略化余地**: typed プロンプト一覧を読み、冗長・重複・貼り過ぎ（長文チャット全文・他 AI 出力の丸貼り等）でトークンを増やしている箇所を、実際の文面を `「…」` で引用して指摘する。
- **聞き返し問題を標準機能で減らせるか**: 「会話密度」（セッション平均プロンプト数・極短プロンプト率）を根拠に、短い往復が多いなら Claude Code 標準機能（plan mode・`/compact`・`/clear` 運用・custom skills・subagents・hooks・output styles 等）で減らせないか評価する。機能の扱い（現在仕様の裏取り・機能名の補足）は「改善提案の共通軸」に従う。
- **無駄トークンの削減**: 「ツール失敗・権限拒否」の失敗率・拒否数を根拠に、失敗した呼び出し（＝往復分の無駄トークン）を permission 設定（settings.json の allow 追加）や手順の定型化で減らせないか評価する。同セクションの「権限未許可で止まった Bash サブコマンド」から、件数の多いコマンドを名指しして `permissions.allow` への追加（`Bash(<サブコマンド>:*)`）か手順の置き換えを提案する（削除・上書き系はまとめて許可せず、確認を残すか対象パスを限定する）。「失敗・拒否の発生箇所（スキル帰属）」で偏りがあるスキルは名指しし、「発生箇所ごとの失敗内訳」の「対象」列（Bash はサブコマンド、Read / Write / Edit はファイル名）と事由まで引用して、そのスキルの SKILL.md のどの手順を直すのかを具体的に書く。そのスキルの手順（コマンドの書き方・前提パス）に原因があるとして具体的に指摘する。「うちサブエージェント」が大半を占める場合は、スキルの手順ではなくサブエージェントへの指示文側の問題として扱う。「スキル別コスト帰属」でコストの大きいスキルがあれば、そのスキルの中身（手順・読み込むファイル量）の見直しも提案する。
- **さらに減らす具体策**: コスト試算の数値に触れて（Step 2 の出力をそのまま引用し推測で作らない）、費用対効果の高い削減策を提案する。キャッシュ効率が高い場合はその旨も添える。

制約:

- コスト・トークン数は必ず analyze.py 出力の数値を引用する。単価は推定であることを踏まえ、断定しすぎない。
- Claude が読めるのはユーザーのプロンプト（collect 出力）だけで、**assistant の出力本文は読めない**。出力の簡略化は output_tokens の量と一般則として述べ、具体文面を断定しない。

### WORKFLOW_EFFICIENCY ブロックの書き方

「トークン（費用）」ではなく「タスクを最短で正しく完了させる」観点で評価・提案する。TOKEN_EFFICIENCY と目的が違うため、費用の話は繰り返さない。定量セクションの「ターン所要時間」「手戻りシグナル（修正語彙・中断・再編集）」「コード変更量（ユーザー手直し率）」「会話密度（聞き返し傾向）」「permissionMode 分布」を根拠に、次の 4 点を箇条書きで書く。

- **完了時間の実態**: 「ターン所要時間」の合計・平均・最長を引用し、往復回数（会話密度）と合わせて 1 タスクにかかっている時間感を評価する。平均が短く往復が多いなら指示の粒度が細かすぎる可能性、最長が突出しているなら 1 指示に詰め込みすぎの可能性を述べる。
- **手戻りの実態**: 「手戻りシグナル」の修正語彙の検出数・率に加え、行動ベースの指標（ESC 中断・Bash 中断・最多再編集ファイル）と「コード変更量」のユーザー手直し率を引用する。該当プロンプトを `「…」` で引用し、確認不足で意図しない実装が生まれた疑いがあれば、着手前に不足していた前提（完成条件・対象ファイル・やらない範囲）を推定で述べる。assistant の出力本文は読めないため、原因は断定せず「〜の可能性」で書く。
- **聞き返し・往復の多さ**: 「会話密度」（セッション平均プロンプト数・極短プロンプト率・AskUserQuestion 回数）を根拠に、着手前の情報不足で往復が増えていないかを評価する。TOKEN_EFFICIENCY と同じ数値を使ってよいが、ここでは「時間・手戻り」の観点で述べる。
- **標準機能・設定での対策**: plan mode（着手前に方針を合意する）・custom skill（確認手順を定型化する）・hooks や settings（着手前チェックを自動化する）等で、手戻り・往復を減らせないか提案する。「検証コマンド実行回数」が少ない場合は、テスト・型チェックを検証手順に組み込む提案も添える。機能の扱い（現在仕様の裏取り・機能名の補足）は「改善提案の共通軸」に従う。

制約:

- 「手戻りシグナル」の修正語彙は保守的な語彙マッチで、誤検知・取りこぼしを含む。検出プロンプトを自分で読み、明らかな誤検知は除いてから引用する。数値は断定しすぎない。ESC 中断・Bash 中断・再編集集中は行動ベースだが、中断・再編集がすべて手戻りとは限らない（方針転換・段階的な編集も含む）。
- assistant の出力本文は読めない。手戻りの原因はユーザーの修正プロンプトからの推定に留め、Claude が何を間違えたかを断定しない。

### MECHANIZATION ブロックの書き方

「同じ判断・同じ手順を繰り返しているなら、仕組みに落として二度考えない」観点で評価・提案する。TOKEN_EFFICIENCY（費用）・WORKFLOW_EFFICIENCY（時間と手戻り）とは目的が違うため、費用や所要時間の話は繰り返さない。定量セクションの「確認プロンプトの回答一貫性」「定型パターン（仕組み化の候補）」「蛇足行動」「Bash コマンド種別」「編集ファイル」「Skill / Workflow 実行回数」を根拠に、次の 4 点を箇条書きで書く。

- **不要な問いかけの特定**: 「確認プロンプトの回答一貫性」の「毎回同じ選択」表を読み、該当する確認を名指しして削除・既定値化を提案する。どのスキルの手順かを特定し（`.claude/skills/*/SKILL.md` を確認する。`<プラグイン名>:<スキル名>` 形式の Skill は実体がプラグイン側にあり、このリポジトリからは直せない旨を添える）、「その SKILL.md から AskUserQuestion の手順を外して既定値 X にする」形まで具体化する。**「回答が分かれる」表の確認は残すべきものなので、削除提案に混ぜない**（分かれている事実を「判断が実際に揺れている箇所」として明示する）。
- **定型パターンの仕組み化**: 「頻出ツール連鎖」から「〇〇したら必ず〇〇している」パターンを読み取り、hooks（`PostToolUse` 等）・custom skill・スクリプトのどれで固定するのが適切かを提案する。「反復 Bash コマンド」は `permissions.allow` への追加かスクリプト化の候補として扱う。設定書式（キー名・matcher）まで書く。
- **蛇足行動の削減**: 「蛇足行動」の各行のうち回数・率が高いものを取り上げ、成果物を変えずに手数だけ削る具体策を書く。プロンプトでの指示・output styles・hooks のどれで抑えるかを示す。回数が少ない行は取り上げない（無理に 4 行すべてに言及しない）。
- **スキル・エージェントの統合**: 「Skill 別実行回数」「Workflow 別実行回数」「永続カスタムエージェント別起動回数」で 0 回が続いているものは削除・統合の候補として挙げる。逆に手動起動（`/name`）ばかりで自動起動が 0 のスキルは、description が実態に合っていない可能性を指摘する。

制約:

- 提案する機能の現在仕様は「改善提案の共通軸」に従って裏取りする。設定キー名・matcher・イベント名を憶測で書かない。
- 「毎回同じ選択」の判定は質問文を正規化して束ねた結果で、可変部（PR 番号・ブランチ名）を落としているため**別種の質問が同一行に混ざる可能性がある**。表の質問文を読み、明らかに別物なら除いてから引用する。
- 回数が閾値ぎりぎり（2〜3 回）のものは「傾向」に留め、断定しない。
- assistant の出力本文は読めないため、ツール連鎖の意図は推定に留める。

### PROMOTION_REASONS ブロックの書き方

`collect` の stdout に出力される「Agent 起動の関連プロンプト」セクションを読んで執筆する。起動回数で絞らず全エージェント分が出るため、**表記が違うだけの同一作業を意味で束ねてから書く**。

- 形式: `エージェント名: 理由テキスト`（1 エージェント 1 行）
- **意味が同じで表記だけ違う行が複数ある場合は、その行すべてに同じ理由を書き、理由文に合計回数を添える**（例: `Anthropic API 単価と USD/JPY 調査: 単価調査で毎回起動しているため。表記の違う同一作業が計 4 件。`）。起動回数で束ねられないため、意味の同一性はプロンプト本文を読んで判断する
- 起動回数がしきい値未満の行にも理由を書ける（★ は付かないが理由は表示される）
- 理由は「〇〇を調べるときに毎回同じ観点で起動しているため。」のように、繰り返している用途を 1 文で書く
- 関連プロンプトは Agent ツールへ渡した指示文そのもの。空になることはほぼ無いが、空だった場合は「（関連プロンプトなし。名前からの推定）」と明記して書く
- エージェント名にコロン（`:`）が含まれる場合（`marketplace:research` 等）も扱える。区切りは「コロン + 半角空白」を優先して判定するため、**理由の前には必ず半角空白を入れる**（`marketplace:research: 理由テキスト`）
