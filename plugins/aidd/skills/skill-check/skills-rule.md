# Skill 作成ルール

Claude Code の Skill を作成する際のルール。公式仕様（フロントマターの全フィールド・文字列置換・動的コンテキスト注入等）はバージョンで変動するため、本ファイルでは重複記述せず公式参照に委ねる。

## 参考公式情報

- [Extend Claude with skills](https://code.claude.com/docs/en/skills) — Claude Code 公式
- [Create plugins](https://code.claude.com/docs/en/plugins) — プラグインとして Skill を配布する場合

## ファイル構造

- 1 Skill = 1 ディレクトリ。エントリポイントは `SKILL.md`
- 補助ファイルはディレクトリ内に配置し、`SKILL.md` から参照する
- プロジェクトスコープの配置先: `.claude/skills/<name>/SKILL.md`
- プラグインとして配布する場合: `<plugin>/skills/<name>/SKILL.md`

```text
my-skill/
├── SKILL.md           # 必須（エントリポイント）
├── reference.md       # 任意（補助ファイル）
├── examples/
│   └── sample.md
└── scripts/
    └── validate.sh
```

## 責務分離

複数ファイル構成の Skill では、各ファイルの責務を明確に分ける。混在させると唯一の情報源が崩れ、ルールが手順から推測しないと分からない状態になる。

| ファイル | 責務 | 含めるもの | 含めないもの |
| --- | --- | --- | --- |
| `SKILL.md` | ルール・補助ファイルを**どう扱うか** | 手順・対象列挙・運用判断・参照先の指示・判定区分 | ルール本体・テンプレート全文 |
| `<name>-rule.md` | **ルール本体**（どう書くか・何を守るか） | 規約・チェックリスト・アンチパターン | 手順・呼び出し方・運用判断 |
| `output-template.md` などの補助ファイル | 単一目的の補助情報 | 出力フォーマット・テンプレート・参考資料 | 判定ルール・手順 |

### 出力形式の委譲

Skill がユーザーやファイルへ出力する形式（テンプレート・サンプル markdown ブロック等）を持つ場合、**`SKILL.md` 本文に出力テンプレートを直接書かない**。原則として `output-template.md`（または用途を表す別名）に切り出し、`SKILL.md` からは参照する。

例外: 出力が 3 行以下の極小スニペット、かつ将来分割の予定がない場合のみ `SKILL.md` 内に置いてよい。

## 命名規約

- `name` は **kebab-case**（小文字 + 数字 + ハイフン）
- 推奨は**動詞 ing 形**（gerund）: `processing-pdfs`、`analyzing-spreadsheets`
- 名詞句・動詞形も可: `pdf-processing`、`analyze-spreadsheets`
- 禁止: `helper`、`utils`、`tools` のような曖昧な名前、予約語 `anthropic` / `claude`
- ディレクトリ名と `name` を一致させる

## description の書き方

- **三人称で書く**。「I can help...」「You can use...」は NG
- 「何をするか」+「いつ使うか」を必ず含める
- トリガーになる具体名詞・動詞を入れる（例: 「PDF」「Excel」「commit message」「diff」）
- 文字数制限など最新仕様は公式参照

| DO | DON'T |
| --- | --- |
| `PDF ファイルからテキストと表を抽出する。ユーザーが PDF やフォーム抽出に言及した時に使用する。` | `ドキュメントを扱う` |
| `ステージング済み diff から Conventional Commits 形式のメッセージを生成する。コミットメッセージを依頼された時に使用する。` | `コミット作成を手伝います` |
| `Excel スプレッドシートを分析し、ピボットテーブルを作成する。.xlsx ファイルや表データを分析する時に使用する。` | `データを処理する` |

## フロントマター運用方針

フィールド仕様は公式参照。運用上は次の方針で記述する。

- 副作用のあるスキル（コミット・デプロイ・送信等）は `disable-model-invocation: true` を必ず設定
- 本文で `$ARGUMENTS` / `$N` を使うなら `argument-hint` を書く
- `allowed-tools` は本文で実行するコマンドを過不足なくカバーする（過剰権限禁止）
- 出力先パスは `Write(<path>)` 権限に含める。ただし**出力先がプロジェクトごとに変わり固定できない場合は含めない**（通常の許可プロンプトを通す方が安全）

プロジェクト独自のメタデータ（文書種別タグ等）を必須にするかは、そのリポジトリの規約で決める。プラグインとして配布する Skill には持ち込まない。

## 本文構造

### 長さ

- **500 行以下**を目標。超える場合は補助ファイルに分割
- 一度ロードされるとセッション中ずっと context に残るためトークン効率が重要

### 簡潔さ

- Claude が既に知っていることを書かない（PDF とは何か、ライブラリの一般論 等）
- 「何をすべきか」を書く。「なぜ」「どう」は最小限
- 段落より箇条書き・表を優先

### 自由度のチューニング

タスクの脆さに応じて指示の細かさを変える。

| 自由度 | 使いどころ | 表現 |
| --- | --- | --- |
| 高 | 複数の正解がある、文脈で判断する | 手順の方向性のみ |
| 中 | 推奨パターンがあるが変動可 | 擬似コード・パラメータ付きスクリプト |
| 低 | 失敗が許されない、順序が厳密 | 具体スクリプトを「このコマンドを変更せず実行」 |

### Progressive Disclosure

参照ファイルは **SKILL.md から 1 階層**まで。多階層は Claude が partial read で取りこぼすリスクがある。

DO:

```text
SKILL.md
├── reference.md
├── examples.md
└── scripts/helper.sh
```

DON'T:

```text
SKILL.md → advanced.md → details.md
```

100 行を超える参照ファイルには冒頭に目次を置く。

### 単一目的の原則

- 1 Skill = 1 関心事
- 2 つ以上のことをやる Skill は分割を検討する
- description で表現できないスコープは含めない

## 補助スクリプトの言語選択

| 言語 | 使いどころ | 例 |
| --- | --- | --- |
| `.sh` | シェル操作中心（git/grep/ファイル走査）、外部 CLI のチェイン、ロジック浅め。**デフォルト** | ファイル走査、git 状態の判定 |
| `.py` | 構造化データ処理（JSON/YAML/CSV）、クロスプラットフォーム要件、複雑な制御フロー・例外処理 | PDF/Excel パース、AST 解析 |

シェルで書ける処理を Python にする必要はない。

## プラグインとして配布する場合の追加ルール

- プラグイン内のファイルは `${CLAUDE_PLUGIN_ROOT}` 起点で参照する。相対リンクはインストール後に解決できないことがある
- **プラグインディレクトリの外を参照しない**（`../../shared` はキャッシュへコピーされないため動かない）
- 利用者が書き換える必要のあるファイル（除外リスト・プロジェクト固有設定）はプラグインに置かず、プロジェクト側を探索する設計にする
- 出力先パスをプロジェクトごとに切り替える必要がある場合、`userConfig` は使えない（プロジェクトの `settings.json` を読まない仕様）。「規約のパスを見る → 候補を探す → ユーザーに聞く」の順で解決する

## アンチパターン

- ❌ Windows 形式パス（`\` 使用）。常に `/` で書く
- ❌ 「pypdf or pdfplumber or PyMuPDF...」のように選択肢を並べる。デフォルトを 1 つ示す
- ❌ 日付固定の指示（「2025 年 8 月以前は...」）。バージョンや状態で書く
- ❌ 用語の揺れ（「field」「box」「element」を混在）
- ❌ エラーを「Claude にお任せ」するスクリプト（処理を投げ返す）
- ❌ 根拠のない定数（`TIMEOUT = 47` のような Magic Number）
- ❌ description を一人称で書く
- ❌ 多階層の参照（A → B → C）
- ❌ シェル操作で済む処理を Python で書く（過剰実装）
- ❌ `SKILL.md` 本文に出力テンプレート（複数行の markdown ブロック・サンプル等）を直接書く（`output-template.md` へ委譲する）

## チェックリスト

### 必須

- [ ] `name` がディレクトリ名と一致（または省略してディレクトリ名に委ねる）
- [ ] `description` が三人称で「何を」「いつ」を含む
- [ ] 本文が 500 行以下
- [ ] 参照ファイルが 1 階層以内
- [ ] パスは全て `/` 区切り

### フロントマター

- [ ] 副作用のあるスキルは `disable-model-invocation: true`
- [ ] `$ARGUMENTS` を使うなら `argument-hint` を書く
- [ ] `allowed-tools` が本文の実行コマンドを過不足なくカバー
- [ ] 固定できる出力先パスが `Write(<path>)` 権限に含まれている

### 本文

- [ ] スコープが description と一致（広すぎず狭すぎず）
- [ ] 用語が一貫している
- [ ] 例が具体（抽象的な「適切に処理する」を避ける）
- [ ] 検証が必要なタスクにフィードバックループがある
- [ ] 内部矛盾がない

### テスト

- [ ] 最低 3 つの代表シナリオで動作確認
- [ ] 使う予定のモデル（Haiku / Sonnet / Opus）で挙動確認
- [ ] 想定外の発火がないか確認
