# Git コミットメッセージルール

Conventional Commits の形式に従い、日本語でコミットメッセージを記述する。

## 基本形式

```bash
<type>: <subject>

Why:
- <なぜこの変更をしたか（1〜2文）>

What:
- <何を変えたか（誰でもわかる平易な言葉で）>

Ref: Issue#<番号>
```

- **scope は使用しない**。`<type>: <subject>` の形式で記述すること
- body が不要なほど自明な変更は、subject のみでよい

## commitlint の制約（必ず守る）

commitlint（config-conventional）で検証するリポジトリでは、違反すると commit が弾かれる。`tmp.md` に書く時点で守る。

- **各行は 100 文字以内**（subject・body・footer すべて）。日本語も 1 文字 = 1 カウント。1 行に収まらない箇条書きは改行して分割する
- **footer の前に空行を 1 行入れる**（`Ref:` / `BREAKING CHANGE:` の直前）
- `type` は次のいずれか: feat / fix / docs / style / refactor / perf / test / chore

> 上限値・許可 type の正典はリポジトリの commitlint 設定（`commitlint.config.*` / `.commitlintrc.*` / `package.json`）。設定が見つかった場合はそちらが優先する。設定が無いリポジトリでも上記の値を目安として守る。

## subject（件名）のルール

- 簡潔に書く（目安 50 文字程度、上限は commitlint 設定に従う）
- 動詞で始める（「追加」「修正」「更新」「削除」「分離」等）
- 句読点（。、）は使用しない
- 「何をしたか」が一目でわかる粒度にする

## body（本文）のルール

全タイプ共通で **Why（なぜ） + What（何を）** の2セクション構成にする。

### 書くこと

- **Why**: なぜこの変更をしたか。1〜2 文で簡潔に書く
  - 新規追加: 「〜する必要があった」と義務形で書かない。何のために作ったか・何ができるようになるかを書く
  - ドキュメント: 「〜できなかった」と課題形で書かない。「〜を理解してもらうため」など目的で書く
  - バグ修正: 「〜したときに〜というエラーが出たため」のように、再現条件と症状を具体的に書く
- **What**: 何を変えたか。誰が読んでもわかる平易な言葉で、箇条書き 2〜5 項目

### 書かないこと

- ファイル名、関数名、クラス名などの変更差分の詳細（diff で確認できる）
- コードの実装手順や技術的な手順書
- 自明な内容の繰り返し（subject で伝わっていることを繰り返さない）

## footer（フッター）のルール

- `Ref: Issue#123` または `Ref: PR#456` で関連リンクを記載
- Issue か PR か不明な場合は `Ref: #123` でよい
- 無い場合は省略
- 破壊的変更がある場合は `BREAKING CHANGE:` を記載

## コミットタイプと例

### feat — 新機能の追加

書くこと: なぜその機能が必要か、何が実現されたか
書かないこと: 実装の技術詳細

```bash
feat: YouTube動画アップロード機能を追加

Why:
- 動画作成からアップロードまでを自動化し、手動作業をなくす

What:
- YouTube Data API v3による動画アップロード機能を実装
- サムネイル画像の自動アップロードに対応

Ref: Issue#45
```

### fix — バグ修正

書くこと: 何が壊れていたか、どう直したか
書かないこと: 正規表現の中身、条件分岐の詳細など

```bash
fix: X投稿URLのパースエラーを修正

Why:
- モバイル版の X 投稿 URL を渡すと、既存パターンに一致せず例外で落ちていた

What:
- 新しいURL形式への対応
- モバイル版URLのサポートを追加

Ref: Issue#123
```

### docs — ドキュメントの変更

書くこと: なぜドキュメントを追加/更新したか
書かないこと: 追加したセクション名の列挙

```bash
docs: READMEにセットアップ手順を追加

Why:
- 新規参加者に環境構築の手順を理解してもらうため

What:
- セットアップ手順と環境変数の説明を追加
```

### refactor — リファクタリング

書くこと: なぜ構造を変えたか、何が改善されたか
書かないこと: 移動先のファイルパスや関数名

```bash
refactor: ストレージ処理の共通化

Why:
- 3つのモジュールで類似したストレージ処理が重複していた

What:
- 共通のストレージ処理を1箇所に集約
- 各モジュールをプラットフォーム固有の処理のみに縮小

Ref: Issue#34
```

### test — テストの追加・変更

書くこと: なぜテストを追加/変更したか
書かないこと: テストケースの一覧やアサーション内容

```bash
test: 伏字処理のオン/オフのテストを追加

Why:
- 環境変数による伏字切り替え機能のカバレッジが不足していた

What:
- 有効/無効の両パターンのユニットテストを追加
```

### chore — その他の変更

書くこと: 何のための設定変更か
書かないこと: 設定値の詳細（diff で確認できる）

```bash
chore: Python依存パッケージを更新

Why:
- 依存パッケージに既知の脆弱性があり、パッチ適用版へ更新する

What:
- requirements.txtの依存パッケージを最新版に更新
```

### perf — パフォーマンス改善

書くこと: 何が遅かったか、どう改善されたか
書かないこと: ベンチマーク数値の羅列

```bash
perf: 画像ダウンロード処理を並列化

Why:
- 画像150枚のダウンロードに5分以上かかっていた

What:
- 非同期並列ダウンロードに変更し処理時間を短縮
```

## 禁止事項

- ❌ type なしの日本語のみのメッセージ
- ❌ 内容が不明確な短いメッセージ（例: 「修正」「更新」）
- ❌ body にファイル名や関数名を列挙すること
- ❌ 1つのコミットに複数の目的の変更を混在させること
- ❌ シンボリックリンクをステージしてコミットすること（編集はリンク元の実体ファイルに対して行う）

## 適用範囲外

Dependabot などが自動生成するコミット（`chore: bump the github-actions group with N updates` 等）。生成側が英語で作るため、日本語化・body の Why/What・`Ref:` の付与は求めない。type だけは本規約に合わせられる場合は合わせる。
