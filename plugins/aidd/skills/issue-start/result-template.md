# 結果の伝え方（issue-start）

手順 16 で結果を伝えるとき、手順 3 で前提が崩れていて止めるときに読む。

## 形

次の形で伝える。中身が無い節は書かない。パスの前後は、半角スペースか改行で区切る（規約は `aidd` の `README.md` の「出力先のパスは、前後を区切って伝える」）。

```markdown
## 判定：<そのまま着手してよい / 漏れ・食い違いがある / 前提が崩れている>

### 確認の結果

- 合っていたこと：<確かめた記述と、確かめた先（ファイル・行・引用元）>
- チェックリストに無い修正箇所：`<ファイル>:<行>` <直す必要がある理由>
- 食い違い・注意点：<記述と今のコードの違い・未確認の引用・既に取りかかっている人など>

### 決めたこと

| 項目 | 決めたこと |
| --- | --- |
| <決めること> | <答え> |

### 実装したこと

- `<ファイル>` <何を変えたか>

### 検査の結果

- `<コマンド>`：<結果>

### Issue の更新

- 本文：<反映した / 反映できなかった（理由）>。書き換える前の本文は `tmp/<ブランチ名>/issue-start/<ts>_issue_before.md`
- 文字数：<数えた文字数> / 500（数えられなかったときは、その理由）

### 作ったもの

- ADR： `<ADR_DIR>/<ファイル>` （<重さ>）
- コミットメッセージ： `tmp.md`
- PR 本文： `tmp/<ブランチ名>/pr-create_<ts>.md`
- 検証コメント： `tmp/<ブランチ名>/pr-verify_<ts>.md`

### ブランチ

- ブランチ：`<ブランチ名>`（<新しく作った / 既存のブランチへ移動した>。起点は `<起点のブランチ>`）
- 担当者：<足した / 既に入っていた / 足せなかった（理由）>

### 残っていること・未確認

- <直せなかった検査・消してほしいファイル・確かめていない挙動など>

### 人がすること

- `tmp.md` の内容でコミットする
- push して、PR 本文のファイルで PR を作る
```

## 前提が崩れているとき

手順 3 で、「判定」と「確認の結果」の節を示して終わる（`errors.md` の「前提が崩れているとき」）。コメントを選んだときだけ、その結果を 1 行で伝える。
