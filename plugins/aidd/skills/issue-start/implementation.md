# 実装と検査（issue-start）

手順 10 で実装するとき、手順 11 で検査するとき、手順 10・11 で人に計測・検証を頼むとき、手順 13 で ADR にするかを聞くとき、手順 12・15 でステージに置くとき、手順 16 で PR の下書きに使う差分を決めるときに読む。

## 実装する

- 計画どおりに直す。リポジトリの `CLAUDE.md`・`.claude/rules/` に従う
- 直した・作ったファイルを控える。手順 12・15 でステージに置くため
- 作業用の一時ファイル（スクリプト・中間ファイル・確認用の画像）は `tmp/<ブランチ名>/work/<目的>/` に置く。`<目的>` は、作業の中身が分かる英語の短い名前にする（例：`merge-conflict`）。消さずに済むようにし、スキルの出力と分けるため
- Python のスクリプトは `python -B` で実行する。`__pycache__` が `tmp/` に残ると、消せないファイルが増えるため
- ファイルを消す必要があるときは、消さずに、消すコマンドを報告に書いて人に頼む。削除は人が行うため。コマンドは `git rm <ファイル>` で書く。削除がステージに置かれ、同じコミットに入るため。`tmp.md` が `git reset` から始まるときは、その後に実行するよう添える。`git reset` が削除を外すため
- 削除が要るときも止まらず、削除前の状態で手順 11・12 へ進み、PR の下書きまで進める。人の削除を待つと、人がいないと下書きまで進めないため。消す予定のファイルは、直したファイルとは分けて控える。手順 11・12 で、そのファイルに出た指摘を分けるため
- 途中で計画に無い判断が要るときは、`AskUserQuestion` で聞く
- 人の手作業が要る計測・検証を頼むときは、下の「人に計測・検証を頼む」に従う

## 検査する

- テスト・Lint・型検査のコマンドを、`CLAUDE.md`・README・`package.json` の `scripts`・`Makefile`・`.github/workflows/` から探して実行する
- 失敗したら直して、もう一度実行する。直せないものは報告に書く
- 消す予定のファイルに出た失敗は直さず、報告の「検査の結果」に「削除で消える失敗」として分けて書く。削除すれば消える失敗を直すのは無駄で、削除後にもう一度実行して確かめるため
- コマンドが見つからなければ実行せず、報告に書く
- 人の手作業が要る計測・検証を頼むときは、下の「人に計測・検証を頼む」に従う

## 人に計測・検証を頼む

人の手作業（エディタの再起動・画面操作・待ち時間など）が要る計測・検証を、利用者に頼む前に当てる。同じ依頼を繰り返すと、利用者の時間を使っても判断が進まないため。

- 頼まずに済むかを先に確かめる。Claude が起動・操作できるもの（開発サーバー・ブラウザ・コマンド・対象のプロセスを直接起動するスクリプト）は、頼まずに自分で行う。人が行うと決まっている操作（ログイン・リモートへの反映・削除など。リポジトリの規約と deny に従う）は、自分で行わずに頼む。この節は、Claude に任せる操作の線引きを変えないため
- 頼む前に、設定や変更が実際に効いているかを Claude が確かめる（プロセスの環境変数・ログなど）。設定を読むコードだけを根拠に、反映の方法を決めない。効いていない状態を測らせないため。環境変数は、確かめる変数の値だけを読む。プロセスの環境変数には、秘密の値も入っているため
- 比べる条件と判定の基準を、頼む前に決めて示す。1 回の結果で判断できるようにするため
- 同じ目的の計測・検証を頼むのは、2 回まで（1 回目と、やり直し 1 回）にする。やり直しを頼むときは、1 回目から何を変えたかを示す
- 2 回で決まらないときは、3 回目を頼まず、手元の結果で決める。確かめられなかった点は、報告の「残っていること・未確認」に書く

## ADR にするかを聞く

手順 8 で決めたことに ADR にできるものがあれば、`adr` の `SKILL.md` の手順 1 のとおり、`AskUserQuestion` で「作らない・極小・簡易・詳細」から選んでもらう。選ばれたものは、`adr` スキルを Skill ツールで呼んで作る（`disable-model-invocation: false` のため呼べる）。無ければ聞かずに手順 14 へ進む。

## ステージに置く

- 控えたファイルだけを `git add <ファイル>` で置く。`git add -A`・`git add .` は、作業中にできたファイル（キャッシュなど）や手順 4 で持ち越した変更が混ざるため使わない
- 手順 12 で置いたファイルを、手順 15 でもう一度置いてよい。点検の後に直した分も入れるため

## 下書きに使う差分

手順 16 では、まだコミットが無い。そのため、コミットの一覧と差分（`git log`・`git diff <起点のブランチ>...HEAD`）の代わりに、ステージ済みの差分（`git diff --cached`）と `tmp.md` のメッセージを使う。前からのコミットがあれば、それも合わせて使う。消す予定のファイルは、まだ差分に入っていないため、PR の下書きの「変更点」と `tmp.md` のメッセージに「削除」として書く。
