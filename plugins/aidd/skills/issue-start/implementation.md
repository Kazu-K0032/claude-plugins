# 仕様の反映から ADR まで

`issue-start` の手順 9〜13 の細部。決めた仕様を Issue に反映し、実装・検査し、Issue のタスクを更新して、ADR にするかを聞く。

## Issue に決めた仕様を反映する（手順 9）

計画の承認の後、実装の前に行う。実装中に、Issue とコードが食い違わないようにするため。

1. 今の本文を `tmp/<ブランチ名>/issue-start/<ts>_issue_before.md` に書き出す
1. 決めたことに合わせて書き換えた本文を `tmp/<ブランチ名>/issue-start/<ts>_issue.md` に作る。「決めること」の節は、答えを書いた「決めたこと」にする。タスクは決めた内容に合わせて足す・書き換える。チェックリストに無い修正箇所もタスクに足す。長さは `short-body.md` に従い、本文全体を 500 文字以内にする
1. 数える。超えていたら縮めて作り直し、もう一度数える。3 回直しても収まらなければ、超えた箇所を報告に書いて反映する。Node.js が無い・実行を断られたときは、数えずに反映し、報告に書く

   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/scripts/body_length.js" tmp/<ブランチ名>/issue-start/<ts>_issue.md
   ```

1. 反映する

```bash
gh issue edit <番号> --body-file tmp/<ブランチ名>/issue-start/<ts>_issue.md
```

止められたら（許可を断られた・フックで止められた）、本文は `tmp/` に残したまま実装に進み、報告に理由と、手で反映する方法を書く。

## 実装する（手順 10）

- 計画どおりに直す。リポジトリの `CLAUDE.md`・`.claude/rules/` に従う
- 直した・作ったファイルを控える。手順 14 でステージに置くため
- 作業用の一時ファイル（スクリプト・中間ファイル・確認用の画像）は `tmp/<ブランチ名>/work/<目的>/` に置く。`<目的>` は、作業の中身が分かる英語の短い名前にする（例：`merge-conflict`）。消さずに済むようにし、スキルの出力と分けるため
- Python のスクリプトは `python -B` で実行する。`__pycache__` が `tmp/` に残ると、消せないファイルが増えるため
- ファイルを消す必要があるときは、消さずに、消すコマンドを報告に書いて人に頼む
- 途中で計画に無い判断が要るときは、`AskUserQuestion` で聞く

## 検査する（手順 11）

- テスト・Lint・型検査のコマンドを、`CLAUDE.md`・README・`package.json` の `scripts`・`Makefile`・`.github/workflows/` から探して実行する
- 失敗したら直して、もう一度実行する。直せないものは報告に書く
- コマンドが見つからなければ実行せず、報告に書く

## Issue のタスクを更新する（手順 12）

手順 9 と同じ手順（書き換える前の本文を書き出し、数えてから反映する）で、実装で埋まったタスクにチェックを入れる。埋まっていないタスクは外したままにする。

## ADR にするかを聞く（手順 13）

手順 8 で決めたことのうち、ADR にできるもの（あとで同じことで迷いそう・次の判断の参考になる）があれば、`AskUserQuestion` で「作らない・極小・簡易・詳細」から選んでもらう。1 回に 4 件まで、おすすめを先頭にする。

選ばれたものは、`adr` スキルを Skill ツールで呼んで作る（`adr` は `disable-model-invocation: false` で呼べる）。作った ADR と、一覧（`<ADR_DIR>/README.md`）も、手順 14 でステージに置く。ADR にできるものが無ければ、聞かずに手順 14 へ進む。
