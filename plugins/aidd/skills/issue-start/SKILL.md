# Issue の着手

Issue の記述が今のコードと合っているかを確かめ、作業用のブランチを用意し、要件を詰めてから実装する。実装の後は、Issue の更新と、コミットメッセージ・PR の下書きまでを済ませる。コミット・push と PR の作成は人が行う。

GitHub に書き込むのは次の 4 つだけ。ラベルと既存のコメントは変えない。

| 書き込み | コマンド | 手順 |
| --- | --- | --- |
| Issue に紐づくブランチの作成 | `gh issue develop` | Step 5 |
| 自分を担当者に足す | `gh issue edit --add-assignee @me` | Step 6 |
| Issue の本文の更新 | `gh issue edit --body-file` | Step 9・12 |
| 着手を見送った理由のコメント（ユーザーが選んだときだけ） | `gh issue comment` | Step 3 |

## 参照ファイル

| ファイル | 役割 |
| --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/references/ai-research.md` | 引用元を確かめた結果の扱い（確かめられなかった引用を「確認済み」としない） |
| `${CLAUDE_PLUGIN_ROOT}/skills/issue-start/comment-template.md` | 着手を見送ったときに Issue に投稿するコメントの形 |
| `${CLAUDE_PLUGIN_ROOT}/skills/commit/SKILL.md` | コミットメッセージの作り方（Step 13） |
| `${CLAUDE_PLUGIN_ROOT}/skills/pr-create/SKILL.md` | PR 本文と検証コメントの作り方（Step 14） |

## 出力先

`tmp/<ブランチ名>/` に書く。ブランチ名の `/` は `-` に置き換える（規約は `aidd` の `README.md` の「ブランチ名の `/` は `-` に置き換える」）。`<ts>` は `date +%Y%m%d_%H%M%S` で取る。

| ファイル | 中身 |
| --- | --- |
| `issue-start_<ts>_issue_before.md` | 書き換える前の Issue の本文（Step 9・12 で、書き換えるたびに残す） |
| `issue-start_<ts>_issue.md` | 反映する Issue の本文 |
| `issue-start_<ts>_plan.md` | 計画モードに入れなかったときの計画（Step 7） |
| `pr-create_<ts>.md`・`pr-verify_<ts>.md` | PR 本文と検証コメント（Step 14） |

コミットメッセージは、`commit` と同じくプロジェクトのルートの `tmp.md` に書く。

## バリデーション

- `$ARGUMENTS` が空の場合は、Issue の番号か URL を質問する
- 識別子は番号でも URL でもよい。`gh` は両方を受け付けるため、パースせずそのまま渡す
- `gh issue view` が失敗したら、その時点で中断して原因を報告する（存在しない・権限が無い・リポジトリが違う）
- Issue の URL のリポジトリが、今いるリポジトリ（`gh repo view` の `nameWithOwner`）と違う場合は中断する。ブランチを作っても、ここでは移動できないため

## 手順

### Step 1: Issue と今の状態を集める

```bash
gh issue view <Issue> --json number,title,body,state,labels,assignees,comments,closedByPullRequestsReferences,url
gh repo view --json nameWithOwner,defaultBranchRef
gh issue develop --list <Issue>
git status --porcelain
git log --oneline --all --grep "#<番号>"
```

`git log --grep` は `#1` で `#10` も拾う。番号が前方一致する別の Issue のコミットは除いて読む。

### Step 2: Issue の記述を確かめる

次の表を上から全て当てる。確かめた先（ファイル・行・引用元の URL）は報告に書くため控えておく。

| 確かめること | やり方 |
| --- | --- |
| 本文とコメントの食い違い | コメントで方針が変わっていないかを読む。食い違えば、新しいコメントの方針を正として報告に書く |
| 本文が指すファイル・行・挙動 | `Read` / `Grep` で今のコードを開き、ファイル名・行の内容・関数名・設定値・挙動が本文の記述と合っているかを確かめる |
| 本文の引用 | 引用元（公式ドキュメント・リポジトリ内のファイル）を開き、同じ文が載っているかを確かめる。Web の引用元は `WebFetch` で開く。開けなかった引用は「未確認」とする |
| チェックリストからの漏れ | Issue に出てくる名前・語句（ファイル名・関数名・スキル名・設定キーなど）で `Grep` し、直す必要があるのにチェックリストに無い箇所を探す。一覧・件数・説明文など、同じ内容を別の場所に書いた箇所を特に見る |
| 着手済みかどうか | Step 1 の紐づいたブランチ・PR・コミット・担当者から、誰かが既に取りかかっていないか、もう実装されていないかを確かめる |
| リポジトリの規約との食い違い | `CLAUDE.md`・`.claude/rules/`・docs の方針を読み、やりたいことが規約に反していないかを確かめる |
| 決めること | 本文の「決めること」と、確かめる中で新たに出てきた判断を一覧にし、それぞれに推奨案と理由を添える |

### Step 3: 判定する

| 判定 | 条件 | 次の動き |
| --- | --- | --- |
| そのまま着手してよい | 記述が今のコード・引用元と合っていて、漏れも無い | Step 4 へ進む |
| 漏れ・食い違いがある | 前提は合っているが、チェックリストに無い修正箇所、記述と今のコードの食い違い、未確認の引用、決めることがある | 止まらずに Step 4 へ進む。見つけたことは Step 8 で扱う |
| 前提が崩れている | 下の止める基準のどれかに当たる | ブランチを作らずに止める（下記） |

止める基準は次の 4 つ。

- Issue が閉じている
- 直す対象のファイル・機能が無い、またはもう実装されている
- Issue が根拠にしている引用が、引用元に無い（開けずに未確認のものは含めない）
- やりたいことが、リポジトリの規約（`CLAUDE.md`・`.claude/rules/`・docs の方針）と明らかに合わない

#### 前提が崩れているとき

Step 15 の形のうち「判定」と「確認の結果」の節で確認結果を示し、止めた理由と、Issue をどう直せば着手できるかを書く。そのうえで `AskUserQuestion` で Issue にコメントするかを聞く。Issue が閉じているときは聞かずに終わる。閉じた Issue に理由を残しても、読む人がいないため。

| 選択肢 | 次の動き |
| --- | --- |
| コメントせずに終わる | そのまま終わる |
| Issue にコメントして終わる | `comment-template.md` の形で本文を作り、下のコマンドで投稿して、結果を伝えて終わる |

```bash
gh issue comment <番号> --body-file - <<'__ISSUE_BODY__'
<テンプレートで作った本文>
__ISSUE_BODY__
```

表やバッククォートを含む本文を `--body` の引数に入れると、シェルのクォートで崩れやすいため、標準入力から渡す。投稿できなかったら（許可を断られた・権限が無い・フックで止められた）、理由を伝えて終わる。

### Step 4: 作業ツリーを確かめる

Step 1 の `git status --porcelain` に出力があれば、ブランチを作る前に止め、`AskUserQuestion` で扱いを聞く。ブランチを移ると、未コミットの変更が新しいブランチへ持ち越されるため。

| 選択肢 | 次の動き |
| --- | --- |
| 中止する | ユーザーが変更を退避・コミットしてから、もう一度呼ぶよう案内して終わる |
| このまま移動する | 変更を持ったまま Step 5 へ進む。持ち越した変更は、Step 13 でステージに置かない |

### Step 5: ブランチを用意する

Step 1 の `gh issue develop --list` に紐づいたブランチがあれば、新しく作らずにそのブランチへ移動する。複数あれば、どれに移動するかを `AskUserQuestion` で聞く。

```bash
git fetch
git switch <ブランチ名>
```

紐づいたブランチが無ければ、ブランチ名を決めてから作る。

1. リポジトリの規約にブランチ名の付け方があれば従う。`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`（`.github/` 配下も）・`docs/` を「ブランチ」「branch」で `Grep` して探す
1. 規約が無ければ `issues/<番号>-<説明>` にする。説明は Issue の要点を英語 2〜4 語の小文字・ハイフン区切りで書く（例: `issues/5-argument-hint`）

```bash
gh issue develop <番号> --name <ブランチ名> --base <既定のブランチ> --checkout
```

- 既定のブランチは Step 1 の `defaultBranchRef` を使い、`main` などに決め打ちしない
- `--base` はリモートにある既定のブランチの最新を起点に作るため、手元の既定のブランチを先に最新にしなくてよい
- 失敗したら（同じ名前のブランチが既にある・書き込み権限が無い等）、エラーを報告して終わる

### Step 6: 自分を担当者に足す

Step 1 の担当者に自分が入っていなければ足す。既に入っていれば実行しない。

```bash
gh issue edit <番号> --add-assignee @me
```

- 他の人が担当者に入っていても外さない。報告の「確認の結果」に書く
- フックなどで止められたら、そのまま進み、担当者を手で足すよう報告に書く

### Step 7: 計画モードに入る

ここまでの確認結果を短く示す（判定・チェックリストに無い修正箇所・食い違い・決めることの一覧）。続けて `EnterPlanMode` で計画モードに入る。計画モードでは計画ファイルしか編集できないため、Issue の更新と実装は、計画の承認の後に行う。

計画モードに入るのを断られたら、計画モードを使わずに Step 8 を行い、計画を `issue-start_<ts>_plan.md` に書く。書いたら、承認を待たずに Step 9 へ進む。

### Step 8: 要件を詰めて計画を作る

決めることを、依存関係でつないだ木として扱う。ある決めごとの答えによって、次に決めることが変わるため。

1. Issue の「決めること」、Step 2 で見つけた判断、計画を書くうえで分からないことを洗い出す。それぞれ、どの決めごとの答えに依存するかを控える
1. 依存する決めごとが全て決まっているものを「今聞ける問い」とし、まとめて `AskUserQuestion` で聞く。1 回に 4 問まで、多ければ分ける。選択肢は推奨案を先頭にし、ラベルに「(Recommended)」を付ける。ほかの問いの答えに依存する問いは、同じ回に入れない
1. 答えを受けて木を更新し、新しく聞けるようになった問いを次の回で聞く。答えで要らなくなった問いは消す
1. 事実（ファイルの中身・既存の作り・使える仕組み）は、利用者に聞かずに自分で調べる（`Explore` エージェントなど）。調べている間も、その事実に依存しない問いは先に聞く
1. 今聞ける問いが無くなったら、計画を書く。決めたこと・直すファイル・Issue をどう書き換えるか・確かめ方を書く。決めることが 1 つも無ければ、質問せずに計画を書く
1. 承認の画面で「Yes, and use auto mode」を選ぶと、確認なしで実装から PR の下書きまで進むことを伝え、`ExitPlanMode` を呼ぶ。「No, keep planning」なら、指摘を受けて計画を直す

### Step 9: Issue に決めた仕様を反映する

計画の承認の後、実装の前に行う。実装中に、Issue とコードが食い違わないようにするため。

1. 今の本文を `issue-start_<ts>_issue_before.md` に書き出す
1. 決めたことに合わせて書き換えた本文を `issue-start_<ts>_issue.md` に作る。「決めること」の節は、答えを書いた「決めたこと」にする。タスクは決めた内容に合わせて足す・書き換える。チェックリストに無い修正箇所もタスクに足す
1. 反映する

```bash
gh issue edit <番号> --body-file tmp/<ブランチ名>/issue-start_<ts>_issue.md
```

止められたら（許可を断られた・フックで止められた）、本文は `tmp/` に残したまま実装に進み、報告に理由と、手で反映する方法を書く。

### Step 10: 実装する

- 計画どおりに直す。リポジトリの `CLAUDE.md`・`.claude/rules/` に従う
- 直した・作ったファイルを控える。Step 13 でステージに置くため
- 作業用の一時ファイルは `tmp/<ブランチ名>/` に置く。消さずに済むようにするため
- ファイルを消す必要があるときは、消さずに、消すコマンドを報告に書いて人に頼む
- 途中で計画に無い判断が要るときは、`AskUserQuestion` で聞く

### Step 11: 検査する

- テスト・Lint・型検査のコマンドを、`CLAUDE.md`・README・`package.json` の `scripts`・`Makefile`・`.github/workflows/` から探して実行する
- 失敗したら直して、もう一度実行する。直せないものは報告に書く
- コマンドが見つからなければ実行せず、報告に書く

### Step 12: Issue のタスクを更新する

Step 9 と同じ手順（書き換える前の本文を書き出してから反映する）で、実装で埋まったタスクにチェックを入れる。埋まっていないタスクは外したままにする。

### Step 13: ステージに置き、コミットメッセージを作る

1. Step 10 で控えたファイルを `git add <ファイル>` でステージに置く。`git add -A`・`git add .` は使わない。作業中にできたファイル（キャッシュなど）や、Step 4 で持ち越した変更を混ぜないため
1. `${CLAUDE_PLUGIN_ROOT}/skills/commit/SKILL.md` を読み、その手順でコミットメッセージを `tmp.md` に書く。コミットはしない

### Step 14: PR の下書きを作る

`${CLAUDE_PLUGIN_ROOT}/skills/pr-create/SKILL.md` を読み、その手順で PR 本文と検証コメントを `tmp/<ブランチ名>/` に書く。まだコミットが無いため、コミット一覧と差分（`git log`・`git diff <既定のブランチ>...HEAD`）の代わりに、ステージ済みの差分（`git diff --cached`）と `tmp.md` のメッセージを使う。ブランチに前からのコミットがあれば、それも合わせて使う。

### Step 15: 報告して終わる

次の形で報告する。中身が無い節は書かない。

```markdown
## 判定：<そのまま着手してよい / 漏れ・食い違いがある / 前提が崩れている>

### 確認の結果

- 合っていたこと：<確かめた記述と、確かめた先（ファイル・行・引用元）>
- チェックリストに無い修正箇所：`<ファイル>:<行>` <直す必要がある理由>
- 食い違い・注意点：<記述と今のコードの違い・未確認の引用・既に取りかかっている人など>

### 決めたこと

| 項目 | 決めたこと |
| --- | --- |
| <決めること> | <答え> |

### 実装したこと

- `<ファイル>` <何を変えたか>

### 検査の結果

- `<コマンド>`：<結果>

### Issue の更新

- 本文：<反映した / 反映できなかった（理由）>。書き換える前の本文は `tmp/<ブランチ名>/issue-start_<ts>_issue_before.md`

### 作ったもの

- コミットメッセージ：`tmp.md`
- PR 本文：`tmp/<ブランチ名>/pr-create_<ts>.md`
- 検証コメント：`tmp/<ブランチ名>/pr-verify_<ts>.md`

### ブランチ

- ブランチ：`<ブランチ名>`（<新しく作った / 既存のブランチへ移動した>。起点は `<既定のブランチ>`）
- 担当者：<足した / 既に入っていた / 足せなかった（理由）>

### 残っていること・未確認

- <直せなかった検査・消してほしいファイル・確かめていない挙動など>

### 人がすること

- `tmp.md` の内容でコミットする
- push して、PR 本文のファイルで PR を作る
```

前提が崩れている場合は、Step 3 で示して終わる。コメントを選んだときだけ、その結果を 1 行で伝える。

## 禁止事項

- ❌ 前提が崩れていると判定したのに、ブランチを作ること
- ❌ 未コミットの変更があるのに、扱いを聞かずにブランチを作る・移動すること
- ❌ Issue のラベルや既存のコメントを変えること
- ❌ 書き換える前の本文を `tmp/` に書き出さずに、Issue の本文を書き換えること
- ❌ ユーザーが選んでいないのに、Issue にコメントすること
- ❌ 既存の担当者を外すこと
- ❌ 紐づいたブランチがあるのに、新しいブランチを作ること
- ❌ ブランチ名・既定のブランチ名を、このスキルの例やリポジトリの慣習から決め打ちすること
- ❌ 引用元で確かめていない引用を「確認済み」と書くこと
- ❌ 決めることを聞かずに、推奨案で実装すること
- ❌ 計画の承認の前に、計画ファイル以外を編集すること
- ❌ コミット・push すること
- ❌ ファイルを消すこと
- ❌ 実装と関係ないファイルをステージに置くこと
