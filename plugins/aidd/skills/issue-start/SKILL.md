# Issue の着手準備

Issue に取りかかる前に、Issue の記述が今のコードと合っているかを確かめ、作業用のブランチを用意する。着手前に漏れ・食い違いを見つけておくと、作業の途中で手戻りが出にくい。

GitHub に書き込むのは次の 3 つだけ。Issue の本文・ラベルと既存のコメントは変えない。

| 書き込み | コマンド |
| --- | --- |
| Issue に紐づくブランチの作成 | `gh issue develop` |
| 自分を担当者に足す | `gh issue edit --add-assignee @me` |
| 確認結果のコメント（ユーザーが選んだときだけ） | `gh issue comment` |

## 参照ファイル

| ファイル | 役割 |
| --- | --- |
| `${CLAUDE_PLUGIN_ROOT}/references/ai-research.md` | 引用元を確かめた結果の扱い（確かめられなかった引用を「確認済み」としない） |
| `${CLAUDE_PLUGIN_ROOT}/skills/issue-start/comment-template.md` | Issue に投稿するコメントの形と書き方 |

## バリデーション

- `$ARGUMENTS` が空の場合は、Issue の番号か URL を質問する
- 識別子は番号でも URL でもよい。`gh` は両方を受け付けるため、パースせずそのまま渡す
- `gh issue view` が失敗したら、その時点で中断して原因を報告する（存在しない・権限が無い・リポジトリが違う）
- Issue の URL のリポジトリが、今いるリポジトリ（`gh repo view` の `nameWithOwner`）と違う場合は中断する。ブランチを作っても、ここでは移動できないため

## 手順

### Step 1: Issue と今の状態を集める

```bash
gh issue view <Issue> --json number,title,body,state,labels,assignees,comments,closedByPullRequestsReferences,url
gh repo view --json nameWithOwner,defaultBranchRef
gh issue develop --list <Issue>
git status --porcelain
git log --oneline --all --grep "#<番号>"
```

`git log --grep` は `#1` で `#10` も拾う。番号が前方一致する別の Issue のコミットは除いて読む。

### Step 2: Issue の記述を確かめる

次の表を上から全て当てる。確かめた先（ファイル・行・引用元の URL）は報告に書くため控えておく。

| 確かめること | やり方 |
| --- | --- |
| 本文とコメントの食い違い | コメントで方針が変わっていないかを読む。食い違えば、新しいコメントの方針を正として報告に書く |
| 本文が指すファイル・行・挙動 | `Read` / `Grep` で今のコードを開き、ファイル名・行の内容・関数名・設定値・挙動が本文の記述と合っているかを確かめる |
| 本文の引用 | 引用元（公式ドキュメント・リポジトリ内のファイル）を開き、同じ文が載っているかを確かめる。Web の引用元は `WebFetch` で開く。開けなかった引用は「未確認」とする |
| チェックリストからの漏れ | Issue に出てくる名前・語句（ファイル名・関数名・スキル名・設定キーなど）で `Grep` し、直す必要があるのにチェックリストに無い箇所を探す。一覧・件数・説明文など、同じ内容を別の場所に書いた箇所を特に見る |
| 着手済みかどうか | Step 1 の紐づいたブランチ・PR・コミット・担当者から、誰かが既に取りかかっていないか、もう実装されていないかを確かめる |
| 決めること | 本文の「決めること」と、確かめる中で新たに出てきた判断を一覧にし、それぞれに推奨案と理由を添える |

### Step 3: 判定する

| 判定 | 条件 | 次の動き |
| --- | --- | --- |
| そのまま着手してよい | 記述が今のコード・引用元と合っていて、漏れも無い | Step 4 へ進む |
| 漏れ・食い違いがある | 前提は合っているが、チェックリストに無い修正箇所や、記述と今のコードの食い違い・未確認の引用がある | 確認結果を示し、進めてよいかを聞く（下記） |
| 前提が崩れている | 下の止める基準のどれかに当たる | ブランチを作らずに、確認結果と止めた理由を示して終わる（下記） |

止める基準は次の 3 つ。

- Issue が閉じている
- 直す対象のファイル・機能が無い、またはもう実装されている
- Issue が根拠にしている引用が、引用元に無い（開けずに未確認のものは含めない）

#### 漏れ・食い違いがあるとき

ブランチを作る前に、Step 7 の形で確認結果を示す（「ブランチ」の節は除く）。そのうえで `AskUserQuestion` で進めてよいかを聞く。漏れ・食い違いによっては、Issue を直してから着手した方がよいため。

| 選択肢 | 次の動き |
| --- | --- |
| 進める | Step 4 へ進む |
| Issue にコメントしてから進める | 確認結果を Issue にコメントしてから（下記の「Issue へのコメント」）、Step 4 へ進む |
| 止める | ブランチを作らずに終わる。Issue を直してから、もう一度呼ぶよう案内する |

#### 前提が崩れているとき

Step 7 の形で確認結果を示し、「ブランチ」の節の代わりに、止めた理由と、Issue をどう直せば着手できるかを書く。そのうえで `AskUserQuestion` で Issue にコメントするかを聞く。Issue が閉じているときは聞かずに終わる。閉じた Issue に理由を残しても、読む人がいないため。

| 選択肢 | 次の動き |
| --- | --- |
| コメントせずに終わる | そのまま終わる |
| Issue にコメントして終わる | 止めた理由を Issue にコメントし（下記の「Issue へのコメント」）、結果を伝えて終わる |

#### Issue へのコメント

ユーザーが選んだときだけ投稿する。`comment-template.md` のテンプレートで本文を作り、標準入力から渡す。表やバッククォートを含む本文を `--body` の引数に入れると、シェルのクォートで崩れやすいため。

```bash
gh issue comment <番号> --body-file - <<'__ISSUE_BODY__'
<テンプレートで作った本文>
__ISSUE_BODY__
```

- 漏れ・食い違いがあるときは「着手前の確認」、前提が崩れているときは「着手を見送った理由」のテンプレートを使う
- 投稿できなかったら（許可を断られた・権限が無い・フックで止められた）、そのまま次へ進み、報告に理由を書く。コメントは経緯の記録で、着手を止める理由にはしない

### Step 4: 作業ツリーを確かめる

Step 1 の `git status --porcelain` に出力があれば、ブランチを作る前に止め、`AskUserQuestion` で扱いを聞く。ブランチを移ると、未コミットの変更が新しいブランチへ持ち越されるため。

| 選択肢 | 次の動き |
| --- | --- |
| 中止する | ユーザーが変更を退避・コミットしてから、もう一度呼ぶよう案内して終わる |
| このまま移動する | 変更を持ったまま Step 5 へ進む |

### Step 5: ブランチを用意する

Step 1 の `gh issue develop --list` に紐づいたブランチがあれば、新しく作らずにそのブランチへ移動する。複数あれば、どれに移動するかを `AskUserQuestion` で聞く。

```bash
git fetch
git switch <ブランチ名>
```

紐づいたブランチが無ければ、ブランチ名を決めてから作る。

1. リポジトリの規約にブランチ名の付け方があれば従う。`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`（`.github/` 配下も）・`docs/` を「ブランチ」「branch」で `Grep` して探す
1. 規約が無ければ `issues/<番号>-<説明>` にする。説明は Issue の要点を英語 2〜4 語の小文字・ハイフン区切りで書く（例: `issues/5-argument-hint`）

```bash
gh issue develop <番号> --name <ブランチ名> --base <既定のブランチ> --checkout
```

- 既定のブランチは Step 1 の `defaultBranchRef` を使い、`main` などに決め打ちしない
- `--base` はリモートにある既定のブランチの最新を起点に作るため、手元の既定のブランチを先に最新にしなくてよい
- 失敗したら（同じ名前のブランチが既にある・書き込み権限が無い等）、エラーを報告して終わる

### Step 6: 自分を担当者に足す

Step 1 の担当者に自分が入っていなければ足す。既に入っていれば実行しない。

```bash
gh issue edit <番号> --add-assignee @me
```

- 他の人が担当者に入っていても外さない。報告の「食い違い・注意点」に書く
- フックなどで止められたら、ブランチはそのままにして、担当者を手で足すよう報告に書く

### Step 7: 報告して止まる

次の形で報告する。中身が無い節は書かない。報告したら止まり、実装に進むかはユーザーの指示を待つ。

```markdown
## 判定：<そのまま着手してよい / 漏れ・食い違いがある / 前提が崩れている>

### 合っていたこと

- <確かめた記述と、確かめた先（ファイル・行・引用元）>

### チェックリストに無い修正箇所

- `<ファイル>:<行>` <直す必要がある理由>

### 食い違い・注意点

- <記述と今のコードの違い・未確認の引用・既に取りかかっている人など>

### 決めること（推奨案）

| 項目 | 推奨 | 理由 |
| --- | --- | --- |
| <決めること> | <推奨案> | <理由> |

### ブランチ

- ブランチ：`<ブランチ名>`（<新しく作った / 既存のブランチへ移動した>。起点は `<既定のブランチ>`）
- 担当者：<足した / 既に入っていた / 足せなかった（理由）>
- コメント：<投稿した（URL） / 投稿できなかった（理由）>
```

Step 3 で確認結果を示した場合は、繰り返さずに「ブランチ」の節だけを書く。「コメント」の行は、ユーザーがコメントを選んだときだけ書く。前提が崩れている場合は Step 3 で示して終わり、コメントを選んだときだけ、その結果を 1 行で伝える。

## 禁止事項

- ❌ 前提が崩れていると判定したのに、ブランチを作ること
- ❌ 漏れ・食い違いがあると判定したのに、進めてよいかを聞かずにブランチを作ること
- ❌ 未コミットの変更があるのに、扱いを聞かずにブランチを作る・移動すること
- ❌ Issue の本文・ラベルや既存のコメントを変えること
- ❌ ユーザーが選んでいないのに、Issue にコメントすること
- ❌ 既存の担当者を外すこと
- ❌ 紐づいたブランチがあるのに、新しいブランチを作ること
- ❌ ブランチ名・既定のブランチ名を、このスキルの例やリポジトリの慣習から決め打ちすること
- ❌ 引用元で確かめていない引用を「確認済み」と書くこと
- ❌ ブランチへ移動した後、そのまま実装に進むこと
