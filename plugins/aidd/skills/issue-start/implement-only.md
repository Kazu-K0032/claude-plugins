# `--implement-only` のときの進め方（issue-start）

`--implement-only` が付いたときに読む。Issue の記述の確認・計画モード・本文の書き換えを省き、変えるファイルの一覧の承認だけを取って、実装から PR の下書きまで進める。`--issue-only` で詰めたばかりの Issue や、もう十分に書かれた Issue で、同じ確認を毎回走らせないため。

## 手順の通し方

| 手順 | `--implement-only` のとき |
| --- | --- |
| 1 | 通す。`issue-checks.md` の「集める」のコマンドを実行し、Issue を読むだけにする。Issue が閉じていれば、ブランチを作らずに止める。コメントするかは聞かない（`errors.md` の「前提が崩れているとき」と同じく、閉じた Issue に理由を残しても読む人がいないため） |
| 2・3 | 飛ばす。記述の突き合わせと判定はしない |
| 4〜6 | 通す。ブランチを用意し、担当者に足す |
| 7・8 | 飛ばす。代わりに、下の「変えるファイルの一覧の承認」を行う |
| 9 | 飛ばす。本文は書き換えない |
| 10〜12 | 通す。一覧どおりに直す |
| 13 | 通す。材料は手順 8 で決めたことではなく、Issue 本文の「決めたこと」にする |
| 14 | 通す。本文は書き換えず、実装で埋まったタスクにチェックを入れるだけにする（`issue-update.md` の手順 14） |
| 15〜17 | 通す。手順 17 は、`result-template.md` の形のうち、行った節だけを書く |

## 止めるとき

次のときは、ブランチを作る前（手順 4 より前）に止める。

- Issue が閉じている：止めた理由を伝えて終わる
- 本文に「決めること」が残っている（「決めること」の節に、答えの無い項目がある）：実装せずに、`--issue-only` で要件を詰めてから呼び直すよう勧めて終わる。決めることを推奨案で実装しないため

## `--issue-only` と両方付いたとき

手順 1 の前に、どちらで進めるかを `AskUserQuestion` で聞く。2 つは行う手順が重ならず、一緒には使えないため。推奨は付けない。

## 変えるファイルの一覧の承認

手順 6 の後、実装の前に、Issue のタスクと「決めたこと」から次の一覧を作って示す。人が実装の前に確かめる場を残すため（P1・V3）。

- 変えるファイルと、それぞれで何を変えるか
- 補足があれば、どう読んだか（P11）
- 確かめ方（Issue の「確かめ方」の節があれば、それに沿う）

続けて、`AskUserQuestion` で 1 回だけ承認を取る。推奨は付けない。

| 選択肢 | 次の動き |
| --- | --- |
| この一覧で進める | 手順 10 へ進む |
| 一覧を直す | 自由記述の指摘を受けて一覧を直し、もう一度聞く |
| 止める | 実装せずに終わる。作ったブランチは残し、報告に書く |

一覧のファイルを変えるタスクが Issue から読み取れないときは、推測で一覧を作らない。`--issue-only` を勧めて止める。

## 書き込むもの

- GitHub：ブランチの作成（手順 5）・担当者の追加（手順 6）・タスクのチェック（手順 14）だけ。本文の書き換え・コメントはしない
- `tmp/<ブランチ名>/` と `tmp.md`：手順 14 の本文（`issue-start/` の下）と、コミットメッセージ・PR の下書き・点検のレポート
