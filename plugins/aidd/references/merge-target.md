# 今のブランチのマージ先の決め方

`pr-create` と `docs-sync` が、今のブランチと比べる先（マージ先）を決める手順。2 つのスキルで同じ先と比べるよう、ここを正典にする。

既定ブランチに決め打ちしない。`develop` に溜めてから `main` へリリースするリポジトリでは、既定ブランチと比べると未リリースの変更まで混ざるため。

## 決める順

1. `gh pr view --json baseRefName` で、今のブランチの PR のマージ先を取る。PR が無ければ（コマンドが失敗したら）次へ進む
1. リポジトリの規約（`CLAUDE.md`・`.claude/rules/`・`CONTRIBUTING.md`（`.github/` 配下も）・`docs/`）を「ブランチ」「branch」「マージ先」で `Grep` し、今のブランチの種類（`issues/`・`develop`・`release/`・`stg` など）のマージ先を読む。ブランチ戦略はリポジトリごとに違う（`develop → stg → main` など）ため、ブランチの種類ごとに読む
   - 今のブランチが「ほかのブランチのマージ先」として書かれているだけの記述は使わない。`develop` で「普段の PR は `develop` へ」を読むと、自分自身と比べてしまうため
1. PR も規約も無ければ、既定ブランチにする。決め方はスキルごとに書く

## 比べる先

- マージ先が決まったら、`git fetch origin <マージ先>` で最新にし、`origin/<マージ先>` と比べる。手元のブランチは、GitHub でのマージに追いつかず古くなりやすいため
- `git fetch` を断られたら、手元の `origin/<マージ先>` で続け、古い可能性を報告に書く
- `origin/<マージ先>` が無いときだけ、手元の `<マージ先>` を使う
- 決めた先と根拠（PR のマージ先・規約のファイル・既定ブランチ）は、報告に書くため控えておく
