# Issue・PR の本文の書き方と長さ

Issue・PR の本文とコメントを、人が読み切れる形にする。冒頭の概要を短く保ち、詳しく書く節はタスクの種類で決め、書かないものを決める。長い本文の全体は読まれなくても、冒頭の概要は読まれ、そこで人が判断できるようにするため。全体の長さで切ると、再現手順や要件のように詳しく書くべき情報まで削られるため、全体には上限を置かない。

## 上限

| 対象 | 上限 |
| --- | --- |
| Issue・PR の本文、Issue・PR へのコメント | 概要（最初の節）を 300 文字以内。概要より後の節は上限なし |
| 検証コメント（`pr-verify`） | なし。項目の数が差分で決まるため |

## 概要の数え方

- 概要は、最初の節。先頭の見出しから、同じ大きさ以上の次の見出しの前まで（先頭が `#` 1 つなら `##` でも区切る）。先頭が地の文なら、最初の見出しの前まで。見出しが無ければ本文全体で、短いコメントは全体が概要になる
- Issue フォームで作った本文は、各欄が `###` の見出しになるため、最初の欄（「概要」など）が概要になる
- 人が見える文を数える。見出し・記号（`#`・`-`・`[ ]` など）も数える
- 数えないもの：HTML コメント、改行、行頭・行末の空白、リンクの URL（`[文字](URL)` は文字だけ数える）
- 定型の節は数えない。見出しに「チェックリスト」か「関連 Issue」を含む節で、下位の見出しも含む。PR ごとに中身が変わらないため

## 書き方（全種類）

- 概要には、目的か結論（何をするか・何が起きたか、なぜか）を書く。人が概要だけで判断できるようにする
- 処理の流れを平易に書く（例：「〇〇したとき、〇〇される」）
- 技術的な内容は、引用かリンクで示す
- 判断の理由は残す
- 書かないもの：調べた経緯、同じ内容の繰り返し、前置き、推測、差分を見れば分かる細部（PR の「Files changed」で見られる）

## Issue の種類ごとの書き分け

Issue は、種類で詳しく書く節を変える。種類は、タイトルと中身から決め、計画や承認の画面で示す。PR には当てない。PR の細部は「Files changed」と、紐づく Issue で見られるため。

| 種類 | 詳しく書く節（上限なし） | 理由 |
| --- | --- | --- |
| バグ修正 | 再現手順・期待した動きと実際の動き・エラーメッセージ（そのまま引用）・原因の根拠（コードやログの引用） | 再現できないと直せず、根拠が無いと直し方を信じられないため |
| 新機能・改善 | 決めた要件（どこに・何を・どんな形で）・確かめ方 | 要件が詳しいほど、人も bot（Issue を読んで実装する Claude）も意図どおりに作れるため |
| 文書・版の更新 | 置かない。概要とタスクだけにする | 目的を果たす難しさが低く、詳しく書くと読む負担が増えるだけのため |

どれにも当てはまらないとき（リファクタリング・調査など）は、一番近い種類に合わせ、どれに合わせたかを示す。

## 既存の本文を直すとき

- 概要が 300 文字を超えていれば、概要を縮める。見出しは残し、中身を言い換えて短くする。概要より後の節は縮めない
- 既存の記述を消す変更になるため、反映前に承認を取る。縮める前の本文は `tmp/` に残す

## 確かめ方

書き終えたら、同梱のスクリプトで概要を数える。超えていたら縮め、もう一度数える。3 回直しても収まらなければ、それ以上は直さず、超えた箇所を利用者に示す。スクリプトは、このファイルから見て `../scripts/body_length.js` にある。実行するパスは、各スキルの参照ファイルの表に書いてある。

```bash
# 下書きのファイルを数える
node <スクリプト> <下書きのファイル>
# 下書きのファイルを作らないときは、標準入力から渡す
node <スクリプト> - <<'__BODY__'
<下書き>
__BODY__
```

- 出力の「概要」を読む。終了コードは、上限内なら 0、超えていれば 1
- 検証コメントは数えない（上限が無いため）
- `allowed-tools` には入れない。同梱のスクリプトの実行のため、許可プロンプトが出る
- Node.js が無い・実行を断られたときは、数えずに進めてよい。そのときは、数えなかったことと理由を報告に書く。各スキルの禁止事項の「数えずに〜しない」は、この場合を除く
