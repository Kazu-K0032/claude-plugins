# ADR に関するルール

このリポジトリでは、技術的な判断を ADR（判断の記録）として `docs/adr/` に残す。ADR の一覧（`docs/adr/README.md`）は `CLAUDE.md` で読み込んでいる。後から来た人が、過去の判断の理由をたどれるようにするため、下の 3 つの条件を満たす判断だけを数行で残す。

## 技術的な判断や Issue の対応を始める場合

- 一覧の題から関係する ADR を探し、開いて読む
- ADR に沿って進める。ADR に反する変更が要るときは、実装の前に利用者に伝え、次のどちらかを選んでもらう
  - 変更のほうを、ADR に合わせる
  - 判断を変える。新しい ADR を足し、古い ADR の状態を「置き換え済み」にする

## 技術的な判断が決まった場合

- 次の 3 つをすべて満たす判断だけを、ADR の対象にする。選ぶ余地の無い作業（誤字の修正・定期の依存更新など）は対象にしない
  - 戻しにくい、または影響が広い（構造・依存・インターフェース・非機能）
  - 比べて見送った案があり、あとで「なぜ A にしなかったか」と聞かれそう
  - 理由を、決定が効く場所（コードのコメント・lint やフックのエラーメッセージ）に書けない（例：JSON の設定、複数のファイルにまたがる決定、ブランチの運用）
- 当たらない判断は、理由（または Issue 番号）をコードのコメントに残す。Claude に守らせたいことは、lint やフックで止める。ADR を読ませるより確実なため
- 作業の区切りで `AskUserQuestion` を 1 回出し、「作らない・極小・簡易・詳細」から選んでもらう。おすすめを先頭にする
- 1 つの判断につき 1 回だけ聞く。「作らない」を選ばれたら、同じ判断では聞き直さない。何度も聞くと、利用者の作業の妨げになるため
- `/aidd:adr` が使えるなら、それで作る。使えないときは、`docs/adr/YYYY-MM-DD-<判断の対象>.md` に題と決めたこと・理由を書き、一覧に 1 行足す。雛形（`docs/adr/*.template.md`）があれば、それを見本にする

## ADR を変える場合

- 作った ADR の本文は書き換えない。判断を変えるときは、新しい ADR を足し、古い ADR の状態を「置き換え済み」にする。どう判断が移ってきたかの履歴を残すため
- 一覧の状態の列も、ADR の状態に合わせる
