# コメントの書き方に関するルール

コード内のインラインコメントには、コードを読んでも分からない「なぜ」だけを書き、既存のコメントは勝手に消さない。コードから読み取れることはコメントに書いても情報が増えず、背景や制約はコメントにしか残せないため。

ドキュメンテーションコメント（JSDoc・PHPDoc・docstring）ではなく、コード内のインラインコメント（`//` / `/* */` / `#`）に関するルール。言語を問わず同じ考え方を適用する。

## コメントを書く場合

「**なぜこのコードを書くか**」だけを書く。コードを読めばわかることは書かない。

```js
// NG: コードそのものを言い換えているだけ（読めばわかる）
const price = item.price; // price を取得する

// OK: なぜこの書き方をしているかを書いている
// 件数カウントのクエリが不要なため省略して応答時間を短縮する
noCount: true,
```

判断の目安: 「このコメントを消しても、コードの意味は変わらないか？」→ 変わらないなら書かない。

### 書くかどうかを決める場合

以下のいずれかに当てはまるとき書く。

- 対話を通じて「これは忘れないようにしたい」と感じたとき
- チームで共有すべき背景・制約・注意点があるとき
- そのロジックがコード全体の中で特に大きな意味を持つとき

### 参照リンクを足す場合

意図の納得感を高めるため、`Ref:` で URL を後に続けてよい。

```js
// structuredClone は循環参照を含むオブジェクトも複製できるため、JSON 経由の複製から置き換えた。
// Ref: https://developer.mozilla.org/docs/Web/API/Window/structuredClone
const copy = structuredClone(state);
```

### 言葉を選ぶ場合

コメントは人が読むものとして書く。**エンジニアだけでなく、PM・デザイナー・技術知識の少ないメンバーが読んでも意図が伝わる言葉を選ぶ**。

- 専門用語・略語・英字コマンドは、初出で一言補足する（例:「www-data（Web サーバーを動かす利用者）」「chown（ファイルの持ち主を変更する操作）」）
- 「なぜこう書くのか」を、前提知識のない読み手でも追えるように書く
- 1 行で足りない背景は「目的 / 理由 / 対応」のように区切ると読みやすい

```sh
# 目的: CI でプラグインを導入できるようにする
# 理由: コンテナごとに利用者 ID が違い、片方が作ったフォルダへもう片方が書き込めない
# 対応: 書き込み対象フォルダだけを誰でも書ける状態にする（使い捨ての CI 環境専用）
chmod 777 upgrade uploads
```

## 既存のコメントを直す・消す場合

- 既存のコメントを**勝手に削除しない**。コードそのものが不要になったときのみ一緒に削除する。コメントには、コードを読んでも分からない背景が残っており、消すと取り戻せないため
- 更新するのは**意図が変わったときのみ**。コメントは「なぜ」を書くものなので、意図が同じなら書き直す必要がなく、書き直すと元の意図が変わってしまうおそれがあるため
- 「なぜ」にあたらないコメント（何をしているかの説明など）であっても削除しない。「なぜ」だけを書くのは新しく書くコメントの基準で、既存のコメントを消す理由にはしないため
