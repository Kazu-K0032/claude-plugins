# 環境変数と設定テンプレート（example）の追従ルール

環境変数を新しくコードで参照したら、対応する設定テンプレート（`*.example`）に必ず追記する。追記漏れは、他の開発者が変数の存在に気づけず設定漏れやテスト失敗を招くため、発見性の担保が目的。

環境変数はどの拡張子のコードからでも生成されうるため、本ルールは `paths` で限定せず常時適用する。

## 原則

- テンプレート（`*.example`）を持つ仕組みで読み込む環境変数を新規に参照したら、同じ変更で対応する example に追記する
- 追記先は「変数を読み込む仕組み」ごとに異なる。仕組みを取り違えない
- テンプレート機構を持たない設定値（言語やフレームワーク固有の定数定義など）は example に書かず、手順書へ書く

| 変数の種類 | 読み込む仕組み | 追記先 |
| --- | --- | --- |
| アプリケーションの env | アプリの設定ローダー（`.env` の読み込み） | `.env.example` |
| テストの env | テストランナーの設定ファイル | `.env.example` |
| コンテナの env | `compose.yaml` | `.env.example` |
| Terraform 変数 | `tfvars` / `TF_VAR_*` | 各環境の `terraform.tfvars.example` |

## テンプレート機構を持たない設定値

`.env` のようなテンプレート機構を経由せず、サーバー上の設定ファイルへ直接書く値は example に書かない。書く先は手順書（`docs/runbook/` 等）とする。

- example に書くと、読み込み機構が対応しないのに存在するように見え、二重管理と誤解を招く
- 同じ値をテスト用に `.env` から読む場合は、そちらは example に書く。設定ファイル側の定数とは別物として扱う

## 追記の体裁

- `変数名=`（空値）または `変数名=サンプル値` の形で書く。デフォルトで有効化すると壊れる変数は空値にする
- 直前に一言コメントを添える（何のための変数か・いつ設定するか）
- 手順の詳細は書かず、SSOT（コード・手順書）へのポインタに留める

```bash
# 検証環境の Basic 認証ユーザー名。検証環境をテスト対象にするときだけ設定する。
# 読み込みはテスト設定の httpCredentials を参照。
E2E_HTTP_USERNAME=
```

## SSOT の分担

- example は「変数の存在＋一言」だけを担う案内役。使い方の手順本体は書かない
- 手順の本体はコード・手順書に置き、example からは参照に留める

## 追記漏れの自動検出（任意）

`pre-commit` フックで「ステージ済みコードが参照する環境変数が example に載っているか」を機械的に検査すると、追記漏れを人の注意力に頼らずに防げる。実行環境が自動で与える標準変数（`CI` / `NODE_ENV` / `PATH` 等）は除外リストに入れる。
