# 設計の方針

3 つのプラグイン（`aidd`・`config`・`project`）を作る・直すときに守る決めごとと、その理由をまとめる。方針は、[AI駆動開発の価値](../values/README.md)を実現するための決めごと。実装で迷ったら、一覧の「読む場面」から方針を探し、そのファイルの Q&A を読む。

| --- | --- | --- |
| [P1](p01-operation-boundary.md) | Claude に任せる操作と、人が行う操作を分けること | コマンドや外部への操作を、Claude に任せてよいか迷うとき |
| [P2](p02-settings-scope.md) | ユーザー全体の設定は config、リポジトリの設定は project が扱うこと | 新しいスキルを、どのプラグインに入れるか決めるとき |
| [P3](p03-check-placement.md) | ADR などの文書は、プロジェクトの規約どおりの場所に置くこと | ADR など、置き場所がプロジェクトごとに違うファイルを作るとき |
| [P4](p04-tmp-output.md) | スキルの下書きやレポートは tmp に出し、コミットに混ぜないこと | レポート・下書き・一時ファイルの置き場所を決めるとき |

## 用語

| 用語 | 意味 |
| --- | --- |
| deny | `settings.json` の `permissions.deny`。ここに当たる操作は、Claude が実行できない |
| `allowed-tools` | スキルの冒頭（frontmatter）に書く、許可を聞かずに実行してよい操作の一覧 |
| 許可プロンプト | Claude が操作する前に、実行してよいかを利用者に聞く確認 |

## ファイルの書き方

方針を足すときは、次の形で 1 方針 1 ファイルを作り、上の一覧と `.claude/rules/plugin-policies.md` の一覧に行を足す。

```markdown
# P<番号> <方針>

| 区分 | 内容 |
| --- | --- |
| 対象 | <この方針を守るプラグイン・スキル> |
| 例外 | <対象のうち、この方針に従わなくてよいものと、その理由> |
| 価値 | <この方針が実現する価値の番号（例：V3）> |

<何をするか・しないかを 1〜2 文で>

## 理由

- <何についての理由か>は、<理由>から

## 変えたいとき

## Q&A

### Q. <実装で迷う場面>

<どうするか。理由>
```

- 方針は「〇〇すること」の形で書く
- 方針の題は、使う人が設計の考え方を分かり、作る人が守ることを分かる言葉で書く。手段（コピーする・tmp に出すなど）ではなく、その目的を書く
- 見出しのすぐ下に、対象を表で書く。行は「対象」「例外」「対象外」「価値」のうち、あるものだけを置く。読んだ人が、自分に関係するかをまず判断できるようにするため
- 「価値」には、この方針が実現する [AI駆動開発の価値](../values/README.md) の番号を書く。プラグインの作りの都合で決めた方針（P2・P5 など）のように、結びつく価値が無ければ省く
- ファイル名は `p<2 桁の番号>-<英語の短い名前>.md` にする
- 番号は使い回さない。廃止した方針の番号は欠番にする。古いリンクや「P5 のため」といった記述が、別の方針を指さないようにするため
- 「理由」は、理由ごとに「- 〜から」の形で 1 項目ずつ書く。理由が 1 つでも同じ形にする
- 理由の先頭で、何についての理由かが分かるように書く（例：「削除は、〜」）
- 「変えたいとき」には、利用者ができること（deny に足す・環境変数で切り替えるなど）を書く
- 「Q&A」には、実装で迷う場面を Q に、どうするかとその理由を A に書く。迷う場面が新しく見つかったら足す
- 段落・箇条書きの 1 項目・表の 1 マスは、それぞれ 200 文字・3 文までにする。1 か所に多くの決めごとを詰めると、読み手が要点を拾えず、読み飛ばすため
- 超えるときは、削って縮めるのではなく、言いたいことを要点の 1 文にまとめて先頭に置き、細部は箇条書き・表に分けるか、Q&A に移す。決めごとを消さずに、読める形にするため
- 書くことが無い節は省く
- `docs/` はプラグインと一緒に配られない。スキルの本文から `docs/` を読ませない（[P5](p05-standalone-plugin.md) と同じ理由。例外は P5 の表）
