# P13 選択肢で聞くのは、人の判断が要る場面だけにすること

| 区分 | 内容 |
| --- | --- |
| 対象 | `aidd`・`config`・`project` のスキルで、`AskUserQuestion` を使う手順 |
| 価値 | [V2](../values/v02-understand-before-accept.md)・[V3](../values/v03-human-judgment.md) |

`AskUserQuestion` で聞くのは、人が決めないと進めない場面だけにする。出力を見てから直せることは聞かずに進め、出力先（`tmp/` のレポート・GitHub など）で確かめてもらう。

- 聞く場面：承認、方針の選択、外への書き込み・削除など取り消しにくい操作の前、費用がかかる処理の前
- 聞かない場面：あとから出力を直せる書き方・細かい既定値の選択

## 理由

- 聞く回数が多いと、中身を読まずに推奨を選びがちになるから
- 選択肢の画面では全体が見えにくく、出力先で見るほうが判断しやすいから
- 承認や方針の選択は人が持つため、その場面では聞くことを省かないから

## Q&A

### Q. 聞くかどうか迷う

出力を見てから直せるなら、聞かない。直せないもの（外への書き込み・削除・費用・結果が大きく変わる方針）なら聞く。

### Q. 聞くときの選択肢

おすすめを先頭に置き、ラベルに「(Recommended)」を付ける。選ぶ前に、判断に要る中身（変更の前後・対象の一覧など）を示す。

ただし、推奨が人の判断を偏らせる場面では、推奨を付けない。例は、実装前に変えるファイルの一覧を承認する質問（`issue-start`）で、一覧を人が確かめて決めるため。
