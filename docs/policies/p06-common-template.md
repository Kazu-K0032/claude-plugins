# P6 土台は共通の考え方だけにし、技術やリポジトリの決まりを上に重ねること

| 区分 | 内容 |
| --- | --- |
| 対象 | `project`（`init-repo`・`gas`・`wordpress`・`terraform`）。「同梱の決まりは既定」は、`aidd`・`project` のスキルと同梱の参照ファイル・雛形 |
| 例外 | 技術に依るが、`init-repo` が配るものが 4 つある（本文の「技術に依るが配るもの」） |
| 価値 | [V3](../values/v03-human-judgment.md)・[V5](../values/v05-mechanisms-over-habits.md) |

土台（`init-repo`）には、どのリポジトリでも共通の考え方だけを入れる。技術の決まりは、技術別のスキル（`gas` など）が決められた場所に後から足す。スキルが同梱する決まりより、リポジトリの決まりを優先する。

## 土台には、どのリポジトリにも要るものだけを入れる

| 項目 | 考え方 | 例 |
| --- | --- | --- |
| 設計思想 | 入れる。どのリポジトリでも同じ運用にする | 権限の線引き（P1）、推論（Claude）と機械の検査の分担、`tmp/` の置き方、ADR、README の案内板、AI が読む文書の書き方（P9）、GitHub の定型（Issue・PR のテンプレート・ラベル・dependabot） |
| 土台自身が動くのに使う技術 | 入れる。土台のフックや CI が動くのに要る | フックの bash・jq、ワークフローの YAML、CI で cspell を動かす Node、CI で zizmor を動かす Python（pipx）とワークフローを読む yq、Lint・整形を動かす lefthook |
| 特定の言語・ツール向けの動く設定 | 入れない。README の「除外したもの」に理由を書く。例示の文で技術名を出すのはよい | ESLint の設定、言語の拡張子の一覧、特定のツールの破壊的な操作の検出 |

### 技術に依るが配るもの

次の 4 つは、土台の考え方に要るか、どのリポジトリに入れても害が無いため配る。

| 配るもの | 技術に依る点 | 配る理由 |
| --- | --- | --- |
| `settings.json` の `env` の `PYTHONDONTWRITEBYTECODE=1` | Python 専用 | Claude の作業スクリプトは言語に関係なく Python で書かれやすく、害も無い |
| `commitlint.config.mjs` | Node のプロジェクトが前提 | コミット規約の検証は土台の考え方で、Node は道具にすぎない。入れる条件で Node のプロジェクトに絞る |
| `docs/architecture/` の構成図の雛形 | AWS を例に描く | 描き方（draw.io のソースと書き出した PNG の対）の見本で、描き直す前提。実物を作ったら雛形の削除を提案する（[P10](p10-template-lifecycle.md)） |
| `lefthook.yml` の `commit-msg` | commitlint を呼ぶ | commitlint が無ければ飛ばすため、どのリポジトリにも害が無い |

## 技術の決まりは、差し込み口に足す

技術別のスキル（`gas` など）は、次の場所にだけ、差分を示して承認を得てから足す。土台が無ければ、先に `/project:init-repo` を実行するかを聞く。土台の規約（P1 の線引き・ADR の置き場所・README の案内板・`tmp/`）に沿い、土台に無い考え方は持ち込まない。

| 場所 | 足すもの | 例（`gas`） |
| --- | --- | --- |
| `.claude/settings.json` | フックと、秘匿ファイルの deny | `guard-clasp.sh`、`.clasprc.json` の deny |
| `.gitignore` | 秘匿ファイル・生成物 | `.clasprc.json` |
| `lefthook.yml` の `claude-edit` | Lint・整形のツール | |
| `.claude/hooks/post-edit-lint.sh` の言語別のブロック | Lint（前の版のフックが残る利用先だけ） | |
| `.claude/hooks/guard-destructive.sh` の `patterns` | 破壊的な操作 | |
| `cspell.json` の `words` | テンプレートが使う語 | `clasprc` |
| `.claude/rules/<技術>.md` | 技術の規約（長ければ `<技術>-<話題>.md` に分ける） | |
| `docs/adr/` | 技術の判断の ADR | |

## 同梱の決まりは既定

スキルが同梱する決まり（書式・本文の長さ・雛形・タイトルの形など）は、リポジトリに同じ話題の決まりが無いときだけ使う。あれば、リポジトリの決まりに従い、決めていない項目だけを同梱の決まりで補う。

- どれに従ったかは、承認の画面か結果に書く。探し方は `plugins/aidd/references/repo-rules.md` にある
- ほかのプラグインと組になる同梱の決まり（`short-body.md`・`markdown.md`）は、`aidd` のファイルを指せないため、探し方を中に書く
- 書き込む先が決まっているスキル（`config:plugin-feedback` は `Kazu-K0032/claude-plugins`）は、探さない

## 理由

- 土台に技術の設定が混ざると、思想だけを入れたいリポジトリに関係の無い設定が入り、どのスキルが何を受け持つかも分からなくなるから
- 技術やプロジェクトで変わるものを土台に入れると、多くのリポジトリで書き換えや削除が要るから
- 配らないと決めた理由が、別のスキルで知らないうちに崩れないようにしたいから
- リポジトリの書き方を決めるのは、そのリポジトリの人だから。2 つの決まりを重ねると `【Bug】fix: 〜` のように形が混ざり、利用者が毎回直すことになる（#200）

## Q&A

### Q. 受け持つ技術別のスキルが無い言語の設定（例：ESLint）を、土台に入れたい

入れない。Lint・整形のツールは、`init-repo` の手順 5 でプロジェクトごとに決めて `lefthook.yml` に書く。言語の規約や構成まで配りたいなら、その言語の技術別のスキルを足す。

### Q. 技術別のスキルが、差し込み口以外を変えたい

変える前に利用者に伝え、差し込み口を増やす（上の表に足す）か、変えるのをやめるかを選んでもらう。

### Q. `init-repo` が配らないファイル（例：ビルドの CI）を、別のスキルで作りたい

`init-repo`・`gas`・`wordpress`・`terraform` の README の「除外したもの」で理由を読み、食い違わないかを確かめる。言語別のルールは技術によって違うため除外しているので、技術別のスキルが配るのは理由に合う。

### Q. リポジトリの決まりが、話題の一部しか決めていない

決めている項目はリポジトリの決まりに、決めていない項目だけを同梱の決まりに従う。例えば、markdownlint の設定で一部の規則だけを切っていれば、残りの規則は同梱の規約で見る。

### Q. リポジトリの決まり同士が食い違う

推測で選ばず、どちらに従うかを利用者に聞く（[V3](../values/v03-human-judgment.md)）。どちらが新しい意図かは、Claude には分からないため。

### Q. 除外した理由と食い違う

作る前に利用者に伝え、除外をやめるか、作るのをやめるかを選んでもらう。除外をやめるなら、README の「除外したもの」の表から消す。
